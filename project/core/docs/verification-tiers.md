# 検証レベルの階層化（Generator / Evaluator 向け）

> 目的: **変更の性質に見合った検証量にする。** すべての変更に同じ重装備の検証を課すと、
> リネーム 1 つでも機能追加と同じコストを払うことになる。
> ただし重い検証は実際に成果を出す（空振りしているテスト・データ層を迂回したテストの検出）。
> **削るのは「効かない場面」に限る。**

コマンド名（`LINT_CMD` など）は **CLAUDE.md の「コマンド」表**が正。ここでは変数名で書く。
スタック固有の検証（DB のゼロベース再生・e2e の回し方・dev サーバーの扱い）は
CLAUDE.md の「スタック: <名前>」節が正。

---

## 1. 判定: 変更が何に触れるか

**触れるものが上位に 1 つでも該当したら、その Tier を適用する。迷ったら上位。**

| Tier | 触れるもの |
|---|---|
| **A（フル）** | （プロジェクトごとに記入: 例 DB スキーマ / 認可 / 決済 / 通知宛先） |
| **B（標準）** | UI・表示 / 既存のサーバー側の更新処理 / データ取得経路 / プラン分岐 / **開発者の DB に書き込む開発用スクリプト**（→ §6） |
| **C（軽量）** | ドキュメント / ファイルのリネーム / 文言 / lint・CI・設定ファイル / テストのみの変更 |

- Tier A の行は初期化（`docs/bootstrap.md`）のときに埋める。**「壊れたら利用者のお金・データ・宛先に実害が出るもの」**を並べる
- **「アプリのソースを 1 行も変えていない」ことは Tier C の根拠にならない。**
  Tier は「何に触れたか」で決まり、「どのディレクトリを触ったか」では決まらない
- **日時・タイムゾーンに触れる変更は Tier B 以上。** Tier C を名乗らせない

## 2. Tier ごとの必須項目

| 検証 | A | B | C |
|---|---|---|---|
| `BUILD_CMD` | ✓ | ✓ | ✓ |
| `LINT_CMD` | ✓ | ✓ | ✓ |
| `TYPECHECK_CMD` | ✓ | ✓ | ✓ |
| `TEST_CMD` | ✓ | ✓ | §2-1 に従う |
| e2e | **全件** | **関連 spec のみ** | 不要 |
| ミューテーション（§4） | **3〜5 個** | **2 個** | 不要 |
| DB のゼロベース再生 | マイグレーションに差分がある場合のみ | 同左 | 不要（マイグレーションのリネームは例外的に ✓） |
| 認可の実測（API 直叩き・サーバー処理の直呼び） | 認可に触れる場合 ✓ | — | — |

- **型検査は全 Tier で必須。** ビルドもテストランナーも lint も、
  「テストが削除済みの API を参照し続けている」型の壊れ方を見ない。
  テストのみの変更（＝ Tier C）こそこの壊れ方の発生源なので、Tier C から外さない
- **DB のゼロベース再生の判定基準は「DB を触ったか」ではなく「マイグレーションの差分の有無」。**
  認可はマイグレーションを 1 本も足さずに変えられる。差分の無い PR で再生しても、
  検証されるのは dev HEAD のマイグレーション群であって PR の差分ではない。
  差分が無ければ PR 本文に「マイグレーションを追加していないため該当なし」と書けば足りる
- **他人の稼働中の DB に対して再生・削除をしない。** 手動テスト用のデータが消える

### 2-1. Tier C の `TEST_CMD`

| 差分の性質 | `TEST_CMD` |
|---|---|
| `docs/**` / `*.md` / コメントのみ | **不要**。ビルド・型検査・lint で足りる |
| `scripts/**` または `.github/**` に差分がある | **全件 1 回・必須**（ビルドも型検査も lint もシェルスクリプトを読まない。テストが唯一の検出経路） |
| アプリのソースを含むが UI・文言のみ | **全件 1 回** |
| 差し戻し後の追加コミットで、差分が上記に収まる | **不要**。前回の測定を流用し、その旨と `git diff --stat` を PR 本文に書く |

### 2-2. 計測は「新しいサーバー」で行う

**長く動かした開発サーバーは、変更を反映しないことがある。** 反映されていないコードで
ミューテーションや before / after を測ると、「変異が生き残った」「回帰した」と**誤報する**。
どれもエラーを出さないので、正しい結果と区別がつかない。

- 計測（ミューテーション / before-after / e2e）は、**計測の直前にサーバーを作り直してから**行う
- **計測中にソースが動いていたら、テストが緑でも結果を使わない**
- サーバーを動かしたまま `git checkout` で before を測らない（一部だけ反映された混成状態を測ることになる）
- 失敗した spec だけを再実行して「直った」と読まない（新しいサーバーで走ったから緑になっただけかもしれない）

原則と作法は `docs/agents/agent-dev-server.md`、具体的なコマンドは CLAUDE.md の「スタック」節。

## 3. 誰が Tier を決めるか

| 役割 | やること |
|---|---|
| Issue の起票者 | **Tier を書かない。** 根拠（何に触るか）だけを書く。書くと Generator も Evaluator もそれを所与として扱い、誰も選び直さない |
| Generator | PR 本文で Tier と根拠を**申告**する |
| Evaluator | **Tier の選択自体が妥当か**を検算する。過小申告なら差し戻す |

PR 本文の書き方:

```
## 検証レベル
Tier B（UI 表示の変更。スキーマ・認可・決済には触れていない）
```

### 3-1. Evaluator は「やり直す」のではなく「検算する」

Evaluator が Generator と同じ検証を最初から全部走らせると、1 PR の往復が倍になる。

**必ず自分で実行するもの（流用禁止）:**

- **ミューテーション**（変異を当てて赤くなるか）。件数と結果まで自分で再現する
- **受入基準の否定側**（拒否されるはずの経路が本当に拒否されるか）
- **DB / 認可に触る PR の DB 実測**（テストの緑ではなく実際の行を見る）
- **画面に出る文言を変えた PR の、実ブラウザでの採取**

**流用してよいもの:** ビルド / 型検査 / lint / テスト / e2e — ただし次をすべて満たすときだけ:

- 差分が DB・認可・日時に及んでいないことを `git diff --stat` で機械的に示す
- 差し戻し後の追加コミットで、アプリのソースの blob SHA が前回検証時と一致する
- dev を取り込んだ後なら、マージ結果のツリーハッシュが自分で測ったツリーと一致することを
  `git merge-tree --write-tree` で示す

**流用したものは、レビュー本文に「流用」と明記する。** 測っていないものを測ったことにしない。
取り込み相手が同じ関数を書き換えていたら、ハッシュが一致していても流用しない。

## 4. ミューテーションの作法と報告

### 4-1. なぜ作法が要るのか — 装置は両方向に嘘をつく

存在しないオプションを渡された装置は、テストを 1 件も走らせずに終わることがある。そのとき

| 装置の読み方 | 出す結論 |
|---|---|
| 「failed の数」を数える | 0 failed = **変異が生き残った**（テストが空振り、と誤報） |
| 終了コードを見る | 非 0 = **変異が殺された**（守られている、と誤報） |

**同じ 1 つの壊れ方が、読み方次第で真逆の嘘をつく。** だから装置に次を必ず持たせる。

### 4-2. 装置の要件（共通ランナーを作るなら全部入れる）

| | 要件 | 欠けると何が起きるか |
|---|---|---|
| ① | テストランナーの**集計行が無い実行は中断**する | 上の両面嘘 |
| ② | 着弾の確認は**変異前のスナップショットとのバイト比較**（`cmp`）。`git diff` は使わない | `git diff` は untracked に対して空を返す。**新しいテストを書いて初めて測るその瞬間**に効かない |
| ③ | **陽性対照**（変異なしで 0 failed）。赤ければ 1 つも変異を撃たない | 赤の原因が変異か元からかを区別できない |
| ④ | 復元はスナップショット + `trap`、復元後に `cmp` で検証。`git checkout` は使わない | 次の変異が前の変異の上に乗る / 他人の未コミットの編集を消す |
| ⑤ | **3 段目**: 新しいテストを潰した写しでは、同じ変異が緑に戻ること | 「たまたま別の既存テストが落ちた」でも killed に見える |
| ⑥ | **着弾「行」の表示**（変更した行を毎回印字し、期待した行に当たったかを照合） | 置換が空振りして無関係な箇所に当たっても「着弾」と出る |
| ⑦ | **テスト総数の減少 / ファイル単位のエラー**を検出したら中断 | 変異で構文が壊れただけの緑を「生存」と誤報する |
| ⑧ | **skip 数の増加**を検出したら中断 | 測定対象が skip されたままの緑を「生存」と読む |
| ⑨ | 作業ツリーが clean でなければ開始しない / 同じ worktree での同時実行を拒否する | 他人の編集が陽性対照に混ざる / 2 本が互いの変異を「復元」する |

**中断はサブシェルの中で起こさない。** `$(…)` の中で中断しても親は止まらず、中断が中断にならない。
装置自身にも「壊すと必ず赤を返す」自己テストを付ける（`docs/agents/quality-gates-shared.md` §1）。

### 4-3. 報告に必ず載せる 3 点

| | 何を | なぜ |
|---|---|---|
| ① | **陽性対照**の集計行 | 前提が壊れていない証明。これが無い報告は数字を検算できない |
| ② | **各実行の集計行の実物** | 「走った」ことの証明。終了コードでは代替できない |
| ③ | **変異の着弾確認**（バイト比較と変更行数） | 「当たった」ことの証明。「`git diff` が空でない」では代替にならない |

### 4-4. 生き残った変異

「N 個中 M 個を殺した」で終わらせない。生き残った変異は、**意味的に等価であることを実測で示す**か、
**テストの穴として Issue を起票する**かのどちらか。殺せた数だけの報告は、空振りしている装置と区別がつかない。

### 4-5. Evaluator 側

- Generator の報告に ①②③ が載っているかを確認する
- **自分の手で 1 つ以上の変異を撃ち、Generator の表と突き合わせる。**
  報告を読むだけでは装置の健全性は確認できない（嘘をつく装置なら陽性対照も一緒に嘘をつく）

## 5. Tier に関わらず常に守ること

時間を食わないので省略しない。

- **否定アサーション（「◯◯が出ないこと」）は、先に肯定側を確定させてから評価する。**
  描画前に「0 件」が成立してしまい、実装を殺してもテストが通る
- **ビューのテストが props 直渡しでデータ層を迂回していないか**を確認する。
  迂回したテストは、データ取得が壊れても緑のまま
- **時刻に依存するテストを、実行環境のローカル時刻で組み立てない。**
  オフセット付きの ISO 文字列で瞬間を固定する（手元と CI / 本番のタイムゾーンは違う）。
  テストは複数のタイムゾーンで走らせ、**走らせるタイムゾーンを減らしたら落ちる**ようにしておく
- **新しい e2e に実行日・実行順への依存を持ち込まない。** 固定日付・座標の決め打ち・
  「並べて 1 件目を掴む」・「現在時刻 + N 日」をそのまま開催時刻にする、はどれも
  特定の曜日・時刻だけ赤くなる。正当な固定値は、その行に理由付きの印を付けて逃がす（ファイル単位の免除は作らない）
- **非同期の状態更新を待つときは「観測可能な状態」を待つ。** 出現だけ待って、まだ無効なボタンを押さない。
  タイムアウトを延ばしても直らない
- **ベースラインとの比較は「合計件数」ではなく「(ファイル, ルール, メッセージ) の多重集合」で行う。**
  合計だけを見ると「1 件直して 1 件増やす」が素通りする
- **免除枠（lint / 型検査のベースライン・除外設定）が広がる方向は、base ブランチの記録と突き合わせて止める**
- **CI の「exit 0」を「検証された」と読まない。** 必須ジョブがそもそも存在しない・skip された、が起こる
- **広域の `pkill` / `killall` 禁止**、**`git reset --hard` / `git clean` / `git stash` 禁止**（並行するエージェントの作業を消す）

## 6. 開発者の DB に書き込む開発用スクリプトは Tier C ではない

**対象:** シード投入・DB の作り直し・掃除など、**開発者の DB に書き込む・作り直す・消す**スクリプト。

Tier 表はアプリケーションの挙動で切られている。シードは「本番の挙動には影響しないが、
**開発者の DB を壊す**」という、表が想定していないリスク軸を持つ。文言どおりに読むと
アプリのソースに触れない大きなスクリプトが Tier C で通り、ガードが効いているかを一度も確かめないまま入る。

| 検証（Tier B に加えて） | なぜ |
|---|---|
| 安全ガード（本番拒否 / 接続先の素性）の**対照実験**: ガードを外した写しが同条件で実際に書き込むことまで見る | 「止まった」だけでは、別の理由で止まった場合と区別できない |
| すべての書き込みスクリプトが「ガード配線テスト」の対象か、理由付きの免除に入っていることを機械で要求する | 宣言し忘れを防ぐ |
| 冪等性の実測（2 回実行して差分 0） | 「2 回実行すると増える」は型でも lint でも出ない |
| 手作りデータが消えないことの実測（消す設計なら、消えることを明示して実測） | 手動テスト用データの喪失は復旧できない |

## 7. PR の粒度と並行

- **関連する Issue は 3〜5 件を 1 PR にまとめてよい。** まとめてよいのは「同じ画面・同じ関数・同じ判定」に触るもの
- **Tier が違うもの（文言 + 認可）を混ぜない。** 混ぜると全体が上位 Tier になる
- **マージは必ず 1 本ずつ。** 1 本入るたびに他の PR の base drift と評決マーカーが無効になる
- 並行させるときは、触るファイルが重ならないようにバッチを組む。重なるなら直列にする
- 同時に資源（dev サーバー・DB スタック）を掴むエージェントは既定 2 体まで（`docs/agents/agent-dev-server.md`）
