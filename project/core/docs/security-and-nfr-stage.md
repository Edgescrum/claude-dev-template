# セキュリティと非機能要件を詰める（ステージの手引き）

> 要件定義書は「何ができるか」で埋まり、**誰が何を見てよいか・どこで止めるか・どこまで耐えるか**が
> 抜けたまま開発に入ることが多い。これらは後から変えると構造ごと作り直しになる
> （例: 認可を DB のポリシーに寄せるか、サーバーのコードに寄せるかは、後から変えると全テーブル・全 API に波及する）。
>
> **決定の記録先は `docs/non-functional.md`**。この文書は「何を聞くか」の手引きで、決定は書かない。

## いつやるか

| 場面 | 範囲 | 誰が |
|---|---|---|
| 新規プロジェクト（`/new-project` の手順 2） | 全項目。**A の項目が決まるまでスタック部品を選ばない** | メインセッションが運用者と grill する |
| 大きめの機能の詳細設計（Planner の計画ワークフロー） | 差分だけ: 新しい資源・ロール・他人のデータの扱い・新しい外部入力・目標値に効く処理 | grill の中で確認し、`docs/non-functional.md` に追記する |

Planner は対話できないので、未決の A 項目を見つけたら論点一覧で停止する（推測で埋めない）。

## 進め方

- 1 項目ずつ聞き、**決定・根拠・（未決なら）仮置きの値と見直し時期**を `docs/non-functional.md` に書く
- 運用者が答えられない項目は、Claude が選択肢と帰結を示して裁定してもらう。**Claude が黙って既定値を入れない**
- **A は「決めない」を許さない。** B は仮置きでよいが、空欄にしない（空欄は「誰も考えていない」と区別できない）
- A2（データアクセス経路）と、標準から外れる A3 の決定は ADR にする（`docs/adr/`）

**脅威の前提: 悪意ある利用者は、正規のアカウントでログインしたうえで、画面を使わずに API を直接叩く。**
画面に出していない・ボタンが無い、は防御にならない。以下の質問はすべてこの前提で考える。

---

## A. 構造に効く項目（決まるまで先に進まない）

| # | 項目 | 聞くこと | 決めないと何が起きるか |
|---|---|---|---|
| A1 | 認可マトリクス | ロール × 資源 × 操作（読む・作る・変える・消す）の表。**他人のデータが絡む行**（事業主が顧客の名前を読む・招待コードを他人が使う・口コミ投稿者名を出す 等）に印を付ける | 実装者ごとに認可の判断が分かれる。印の行が多いほど A2 の選択が効く |
| A2 | データアクセス経路 | ブラウザから DB の公開 API を使うか、サーバーだけが DB に触るか（下の判断表） | 後から変えると全テーブル・全 API の作り直し。公開 API を開けたまま「サーバー経由のつもり」でいると、サーバー側の認可チェックは防御になっていない |
| A3 | 認証とセッション | ログイン方式 / セッションの保管場所（httpOnly Cookie か）/ **ブラウザに DB 用のトークンを渡すか**（A2 と整合させる）/ 管理者の認証強度（二要素）/ 退会・アカウント連携 | トークンをブラウザに渡すと、A2 で「サーバー専用」を選んでも利用者が自分のトークンで直接叩ける |
| A4 | テナント分離 | 1 つの DB で分けるか / 分離キー（`tenant_id` 等）/ 取り違えを機械的に止める保険（DB のポリシー・制約・テスト）/ 運用者がテナントを横断して見る経路 | 1 か所の書き忘れで他社のデータが見える。運用者用の横断経路が無いと、本番調査のたびに保険を外すことになる |
| A5 | 秘匿情報の分類 | 個人情報の一覧 / **未認証に見せてよい列** / 推測不能な URL で配る資源（共有リンク・カレンダー購読）/ 鍵の置き場所と、全権の鍵（DB の service key 等）を使ってよい経路 | 公開してよい列が決まっていないと、列を 1 つ足すたびに漏れる。全権の鍵の使用範囲が決まっていないと、認可の穴埋めに全権の鍵が使われ始める |
| A6 | 外部からの入力 | webhook の署名検証 / 公開フォーム・公開 API のレート制限とボット対策 / ファイルアップロード（種類・大きさ・置き場所・公開範囲） | 署名を見ない webhook は誰でも叩ける。レート制限が無いと、通知・メール・外部 API の従量課金がそのまま攻撃面になる |

### A2 の判断表

| | (a) 公開 API + DB のポリシー（RLS 等） | (b) サーバー専用 |
|---|---|---|
| 仕組み | ブラウザ（またはブラウザの持つトークン）が DB の公開 API に届く。認可は DB のポリシーと、DB 内の関数に書く | 公開 API を閉じる。サーバーが**必要なテーブルにだけ権限を持つロール**で接続し、認可はサーバーのコードに書く。DB のポリシーはテナント取り違えの保険にだけ使う |
| 向いている | 「自分のデータだけ」を扱うアプリ / リアルタイム購読が中心 | 業務系・予約・マルチテナント / **A1 で他人のデータが絡む行が多い** |
| 難しさ | 他人のデータが絡む要件ごとに、認可を内蔵した DB 関数・実行権限の管理・DB テストが要る（関数自体はポリシーをバイパスし、しかも公開 API に出る） | リアルタイム購読などブラウザから直接使いたい機能は、個別に開ける設計が要る |
| 2 層になるか | ブラウザのトークンで直接叩けるので、**サーバー側の認可チェックは層にならない**（実質 DB のポリシーだけ） | サーバーの認可 + DB の保険の 2 層。**ただし A3 でブラウザに DB 用トークンを渡さないことが条件** |

**どちらの場合も、全権の鍵（ポリシーを完全にバイパスする鍵）を利用者の操作で動く経路で使わない。**
使ってよいのは cron・webhook・通知送信など、利用者のセッションが無いシステム経路だけ。

## B. 仮置きでよい項目（数値と見直し時期を書く）

| # | 項目 | 聞くこと | 決めないと何が起きるか |
|---|---|---|---|
| B1 | 規模 | 1 年後の利用者数・テナント数・データ量・ピーク時の同時利用 | 性能目標とプラン選択（DB・ホスティング・外部サービス）の根拠が無い |
| B2 | 性能目標 | 主要画面の表示（例: p75 LCP 2.5 秒）/ 主要 API の応答（例: p95 500ms）/ 重い処理（集計・一括送信・エクスポート）の上限時間 | 遅いと感じた時点で比較の基準が無い。重い処理がリクエスト内に書かれ、タイムアウトで初めて気づく |
| B3 | 可用性 | 許容できる停止時間 / メンテナンスの時間帯 / **依存サービスが落ちたときの振る舞い**（決済・通知・認証がそれぞれ落ちたら、利用者に何を見せ、何を後で再送するか） | 外部障害がそのまま自社障害になる。二重課金・通知の取りこぼしが起きる |
| B4 | データのライフサイクル | 保持期間 / 退会時（削除か匿名化か・他者の記録として残すものは何か）/ バックアップと復旧目標（RPO・RTO）/ **復旧手順を一度試したか** | 退会時に関連データが壊れる。バックアップが「あるはず」のまま、復旧できないことに事故当日に気づく |
| B5 | 法令・規約 | 個人情報保護法（利用目的・第三者提供・海外のサービスへの保存）/ 特定商取引法の表記 / 利用規約・プライバシーポリシー / 計測ツールの同意 / 業界固有の規制 | 公開直前に文言と画面の作り直し。計測ツールの導入後に同意の取り直しが要る |
| B6 | 監査・証跡 | 誰が何を変えたかを残すか（管理者操作・課金・権限の変更・個人情報の閲覧）/ 保持期間 | 問い合わせ・不正の調査ができない。後から足しても過去分は戻らない |
| B7 | 監視と運用 | エラー監視・アラートの送り先 / **誰が何分以内に見るか** / ログの保持期間 / 本番調査の権限（読み取り専用の原則） | アラートが誰にも読まれない。調査のたびに本番の書き込み権限が使われる |
| B8 | コストと外部サービスの上限 | 各サービスのプランと上限 / **上限を超えたら何が起きるか**（課金が増えるのか、止まるのか）/ 月額の上限 | 無料枠の超過で機能が黙って止まる（`docs/bootstrap.md` の「外部サービスの上限」表と同じものを指す） |
| B9 | 対応環境 | 対応ブラウザ・端末・**アプリ内ブラウザ**（LINE・SNS 等）/ アクセシビリティの水準 / タイムゾーン・通貨・言語 | 特定の環境でだけ動かない不具合が本番で見つかる。日時の扱いが実装者ごとに分かれる |
| B10 | 拡張の見込み | 1 年以内に来そうな要件（複数人での利用・多店舗・権限の細分化・外部連携・API 公開）のうち、**A の決定を壊すもの** | A1・A2・A4 を「今の要件だけ」で決め、拡張時に作り直す |

---

## 終わりの条件

- `docs/non-functional.md` の A 全行に決定と根拠がある。A2 の ADR がある
- B 全行が「決定」か「仮置き + 見直し時期」で埋まっている
- 未決の論点が残るなら、その一覧と、それぞれを誰がいつ決めるかが書いてある
- スタック部品の選択が A の決定と矛盾しない（例: A2 で (b) を選んだのに、(a) 前提の部品の規則をそのまま入れていない）
