# 本番への出し方 — リリースと hotfix の 5 経路

> 「hotfix も dev → staging → main の順」という規則は、staging に未リリースの機能が乗っている期間は守れない。
> **規則を実態に合わせ、経路ごとの条件と手順を固定する。**
> スタックに依存する部分（マイグレーションの確認・外部サービスの設定の突き合わせ）は
> **採用スタック部品の runbook 補足**（`docs/runbooks/release-supplement-*.md`）を見る。
> 検証コマンドは CLAUDE.md の「コマンド」表が正。

## 0. 前提: なぜ 1 本の経路では足りないか

- **staging は未リリースの機能を抱える。** 大きな機能が staging で UAT 待ちの間に、
  別の修正だけを本番に出したい場面が繰り返し来る。PR③（staging → main）にすると全部乗る
- **main への取り込みは squash なので、main と staging の履歴が分かれる。** 全量リリースでも
  素直な PR③ がコンフリクトすることがある
- **dev が唯一の正。** どの経路でも、dev に無い変更が本番にだけ残る状態を作らない（作ったら当日中に同期する）

## 1. 経路の一覧

| 経路 | 使う場面 | 起点 | 本番に入れる PR | 典型例 |
|---|---|---|---|---|
| **R1 全量リリース** | staging の内容を丸ごと出してよいとき | staging | PR③（素直にマージできなければ、staging と同一ツリーのリリースブランチ） | スプリントの区切りで UAT を通った全機能を出す |
| **R2 選択リリース** | dev にマージ済みの一部の変更だけを先に出す | main | `release-<テーマ>-<YYYYMMDD>`（dev の squash コミットを cherry-pick） | 分析の計測だけ・表示の不具合修正だけを先に出す |
| **R3 staging 先行 + 選択リリース** | R2 のうち、本番前に実機・実サービスで確かめたいもの | main / staging | 先に staging へ cherry-pick（`…-stg`）、確認後に main へ同じ内容（`…-main`） | 認証・課金・外部プラットフォーム連携の修正 |
| **R4 緊急 hotfix** | 本番が壊れて利用者に影響が出ており、**dev に修正がまだ無い** | main | `hotfix/<Issue番号>-main`（main 上で直す） | ログインできない・決済が通らない |
| **R5 本番の手動処置** | 数分単位で止血が必要で、コードの経路を待てない | 本番の DB / 管理画面 | なし（後から R2 / R4 で恒久化） | 危険な権限の即時剥奪・誤設定の差し戻し |

### 選び方

```
本番で利用者に影響が出ているか？
├─ いいえ → staging を丸ごと出してよいか？
│           ├─ はい → R1
│           └─ いいえ → 本番前に実機・実サービスで確かめたいか？ → はい R3 / いいえ R2
└─ はい → 数分で止血が必要で、コードの経路を待てないか？
          ├─ はい → R5（直後に恒久化の経路へ）
          └─ いいえ → 修正は dev にマージ済みか？
                      ├─ はい → R2（認証・課金・外部連携なら R3）
                      └─ いいえ → dev で数時間以内に直せるか？ → はい: dev で直して R2 / いいえ: R4
```

**R4 は最後の手段。** dev を経由しないので、同期を忘れると次の R1 / R2 で本番の修正が巻き戻る。
数時間待てるなら、dev で通常の PR①（Generator → Evaluator）を通してから R2 で出すほうが安全。

## 2. R2 / R3 の手順（cherry-pick による選択リリース）

1. **dev で完了させる。** 出したい変更は、通常の PR① として dev にマージ済みであること
2. **ブランチを切る。** main から `release-<テーマ>-<YYYYMMDD>`（R3 の staging 側は `…-stg`）
3. **cherry-pick する。** dev の squash コミットを、元 PR の番号と dev 側の SHA を控えながら取り込む。
   **その変更を緑に保つために後から入った修正（テスト修正など）も一緒に入れる**
   （入れ忘れると main の post-merge 検証が赤になる）
4. **dev との一致を機械で検算する。** 触ったファイルごとに dev とバイト比較し、`IDENTICAL` / `DIFFERS` の表を
   PR 本文に貼る。`DIFFERS` は 1 件ずつ理由を書く
5. **スタック固有の確認をする。** 採用スタック部品の runbook 補足（`docs/runbooks/release-supplement-*.md`）を
   最初から最後まで通す（例: マイグレーションの衝突・適用済みの削除・外部サービスの購読設定）
6. **検証する（終了コードを直接確認）。** CLAUDE.md の「コマンド」表の
   `INSTALL_CMD` / `TYPECHECK_CMD` / `LINT_CMD` / `TEST_CMD` / `BUILD_CMD` と、
   `bash scripts/check-commit-authors.sh`
7. **PR を出す。** 本文の必須節:
   - これは何（cherry-pick したコミットと元 PR の表）
   - **PR③ にしなかった理由**（staging が何を抱えているか）
   - 含めていないもの（同じ時期の別変更・適用済みのもの）
   - dev との一致の検算表と `DIFFERS` の理由
   - 検証結果（表）と、R3 なら staging での動作確認の記録
   - 本番適用後の監視（何を・どこで・いつまで見るか）と、ロールバックの判断基準
   - `closes` の扱い（監視が終わるまで閉じない Issue はそう書く）
8. **マージはユーザー専権**（PR③ と同じ）。マージ後: main の post-merge 検証が緑・
   スタック固有の適用（マイグレーション等）が緑・本番での着地確認（**送信側の成功ではなく受信側で確かめる**）・監視の開始

## 3. R4 の手順（main 起点の緊急 hotfix）

1. Issue を起票する（ラベル `hotfix`）。影響範囲と、なぜ R2 を待てないかを書く
2. main から `hotfix/<Issue番号>-main` を切り、最小の修正を入れる。検証は R2 の 5〜6 と同じ
3. **Evaluator のレビューを通す**（緊急でも省略しない。base が main でも、評決をコメントとラベルで残す）
4. マージはユーザー専権
5. **当日中に dev へ同期する。** 同じ修正を dev 宛ての PR① で入れる（cherry-pick + dev 側の差分調整）。
   同期 PR の本文に「main に入った hotfix の PR 番号」を書き、Issue は**同期がマージされてから**閉じる
6. staging にも必要なら、同期後の次の昇格で入る（staging だけ古いまま本番に追い越されている期間を記録する）

## 4. R5 の手順（本番の手動処置）

- CLAUDE.md の「本番環境へのアクセス規律」どおり、**対象・内容・理由を示して運用者の許可を都度得る**
- 実行した操作（SQL・設定変更）をそのまま Issue に記録する（後からコードにするため）
- 当日中に R2 または R4 で恒久化する（DB なら、本番の履歴と食い違わないマイグレーションとして dev に入れる）

## 5. R1 の注意（全量リリース）

- PR③ が squash の履歴差でコンフリクトする場合は、**staging と同一ツリーのリリースブランチ**を作り、
  main を `-s ours` で吸収してから PR にする。ツリーが staging と一致することを `git rev-parse <branch>^{tree}` で検算する
- staging に R3 / R4 由来の個別適用が入っているときは、runbook 補足の「統合先にだけ入った変更」の確認を必ず行う

## 6. どの経路でも守ること

- **dev が唯一の正。** 本番にだけある変更を残さない（R4 / R5 は当日中に dev へ）
- **main へのマージはユーザー専権。** Orchestrator・サブエージェントは main にマージしない
- **本番の監視を決めてから出す。** 何が起きたら戻すか（ロールバックの判断）も PR 本文に書く
- **post-merge 検証の赤は放置しない。** スケジュール実行の結果は対象ブランチを確かめてから読む
