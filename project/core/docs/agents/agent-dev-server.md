# エージェントが開発サーバーを立てる（起動から**片づけまで**）

> **この文書が唯一の置き場所（原則）。** CLAUDE.md やエージェントのブリーフに書き写さないこと。
> 対象: Generator / Evaluator / Orchestrator、および隔離 worktree で開発サーバーを立てる全員。
> **具体的なコマンド（起動・確認・停止・計測）は CLAUDE.md の「スタック」節が正。**
> ここには、どのスタックでも守る不変条件だけを書く。

---

## 0. 資源の規律

**片づけは義務であり、任意の親切ではない。**

- 作業が終わったら、**成否に関わらず、報告を書く前に**自分が起動したサーバーと DB スタックを止める
- e2e とビルドは必要最小限に絞る（何を回すかは `docs/verification-tiers.md` が正）
- **同時に資源を掴むエージェントの数は固定しない。起動の前に、マシンの空きを見て決める**（判定は下の表）

なぜ判定が要るか: 開発サーバー 1 本で数 GB、隔離 DB スタック 1 個で 10 前後のコンテナを掴む。
個々の片づけが効いていても、**空きを見ずに同時実行を増やすと**稼働中のぶんだけでスワップが枯渇する。
原因を「片づけ漏れ」と取り違えると、対策が「もっと片づけろ」になり効かない。
逆に固定の上限は、資源に余裕のあるマシンで並行できる作業まで直列にしてしまう。

| 見るもの | 確かめ方（macOS の例。Linux は `free -m` / `nproc`） | 1 体追加してよい目安 |
|---|---|---|
| 空きメモリ | `memory_pressure \| tail -1` | 空きが 30% 以上あり、追加する 1 体ぶん（目安 4GB）を引いても 20% を割らない |
| CPU | `uptime` の 1 分平均と `sysctl -n hw.ncpu` | 1 分平均がコア数の 70% 未満 |
| 稼働中の資源 | `docker ps`・自分たちが起動した dev サーバー | 片づけ漏れが無い（あれば先に回収してから判定し直す） |

- 稼働中に空きメモリが 20% を切るか、1 分平均がコア数を超えたら、新しく起動せず、走っているものの終了を待つ
- フル e2e・本番ビルドのような重い処理は、同時に 1 つまでにする（負荷の衝突で偽の赤が出る）
- 起動した数と根拠（空きメモリ・1 分平均）を、Orchestrator の報告に 1 行残す

ドキュメントだけを触る作業など、サーバーもスタックも要らないエージェントは枠に数えない。

## 1. 3 つの不変条件

### 1-1. 共有された固定値を持たない

| してはいけない | こうする |
|---|---|
| 全エージェントで同じポート | **worktree の絶対パスから決定論的に採番**する。埋まっていれば次を試し、**実際に使った値を記録**する |
| `/tmp/xxx.pid` のような共有 PID ファイル | `<worktree>/.dev-server/state`（gitignore 対象） |
| `/tmp/xxx.log` のような共有ログ | `<worktree>/.dev-server/dev.log` |

運用者が前景で使うポートは採番対象から外す。**ポートを手で決めない**（`PORT=` も `--port` も通常は使わない）。

なぜ: 並走する別エージェントと同じポートを奪い合うと、自分の起動は失敗したのに
**相手のサーバーが 200 を返し、別の PR のビルドに対してスモークテストを打つ**ことになる。

### 1-2. 「200 が返った」を起動成功の証拠にしない

起動コマンドは、HTTP を打つ**前に**次を確かめてから成功を返す。

| 検査 | 何を否定できるか |
|---|---|
| (a) 自分が起動したプロセスが生きている | 即死した場合だけ |
| (b) 起動ログに「アドレス使用中」等の失敗が無い | ログに出る失敗だけ |
| (c) ★ **そのポートを listen している PID が、自分が起動したプロセスの子孫である** | **他人のサーバーが応答していること** |

**(c) だけが「他人のサーバーを測っている」事故を止める。** (a) と (b) は何も否定しない。
親子関係は推測ではなく OS が持つ事実なので、プロセス名（起動後に書き換わることがある）より信頼できる。

**スモークテストと e2e の直前には、同じ検査をもう一度打つ。** 起動から時間が経つと、
自分のサーバーが落ちて他人が同じポートを掴んでいることがある。

### 1-3. 後片づけは名指しでしか殺さない

- 止めるのは**記録した PID（のプロセスグループ）だけ**
- **`lsof -ti tcp:<port> | xargs kill` を打たない。** 掴んでいるのが誰であっても殺す
- **`pkill` / `killall` を打たない**
- 記録した PID を殺す前に、**記録した起動時刻（`ps -o lstart=`）と一致するか**を確かめる。
  PID は再利用される。一致しなければ 1 件も kill しない
- 孤児になった listener を追撃してよいのは「いま自分の子孫である（その祖先が自分のものと確認済み）」か
  「記録した起動時刻と一致する」ときだけ。**「node っぽいから」で代用しない**
- 記録の worktree がいまの worktree と違えば、何もせずに拒否する
- 停止後もポートが埋まっていたら、PID とコマンドラインを報告するだけで触らない
- 「止めた」と報告するのは**実際にプロセスが消えたときだけ**

## 2. 「自分のサーバー」は「正しいコード」ではない

1-2 の素性検査が言えるのは**誰のサーバーか**だけで、**いつのコードを実行しているか**は何も言わない。
長く動かした開発サーバーには、次の嘘つき経路がある（どれもエラーを出さない）。

| 症状 | 出力から区別できないもの |
|---|---|
| 稼働中のサーバーが一部のモジュールの変更を反映しない | 「変異をテストが殺せなかった」と「サーバーが古い」 |
| サーバーを動かしたまま `git checkout` で戻すと、一部（CSS など）だけ反映される | before の実測と、どちらのツリーにも無い混成状態 |
| 長く動かしたサーバーが、実在する行でも 404 を返す | e2e の「本物の赤」と「サーバーの寿命」 |

**気をつけている人でも踏む。** だから手順ではなく機械で潰す。計測用のラッパーに次を持たせる。

| 仕掛け | 何をするか |
|---|---|
| **ソース指紋** | 起動時に「何をコンパイルしたか」を内容ハッシュで記録する（ソース・設定ファイル・**接続先を決める env ファイル**を含める） |
| 起動時の比較 | 前回コンパイルした指紋と違えばビルドキャッシュを捨ててから起動する |
| 再起動コマンド | 指紋が同じでもキャッシュを捨てて立て直す（寿命の問題は指紋では捕まらない） |
| 確認コマンド | 素性に加えて「起動後にソースが動いていないか」を見る。動いていたら計測不成立 |
| 計測コマンド | 必要なら作り直してから測り、**計測後にもう一度指紋を見て、変わっていたら計測不成立**（テストが緑でも） |

計測コマンドの終了コードは 3 値にする: `0` = 緑 / `1` = 本物の赤 / `2` = **計測が成立していない（結果を使ってはいけない）**。

ビルドキャッシュを消すのは「自分の worktree のもので、いま誰も使っていない」と確認できたときだけ。
使用中の印（ロックファイルに書かれた生きている PID 等）があれば 1 バイトも消さずに止まる。

### 本番モード（ビルド + 起動）で確かめるとき

本番モードでしか出ない不具合を測るときも、自作の `nohup … & echo $! > pid` を使わない。

- **ラッパーの PID と、ポートを掴んでいるプロセスの PID は別物**になりやすい。`kill $(cat pid)` は listener を止めない
- その状態で次のビルドを起動すると、新しいほうが即死し、**前のビルドが 200 を返し続ける**
- 本番モードはソースの変更を一切反映しない。before / after の間には必ず「ビルドし直して立て直す」を挟み、
  **動いているビルドの ID がディスクのビルドと一致するか**を計測の直前に確かめる
- 開発サーバーとビルドを同じ worktree で並走させない

---

## 3. 手で計測するとき

ブラウザ自動操作のツールなどで手で測る場合は、計測コマンドを通らない。
**測る前に再起動、直前に確認コマンド**を自分で打つこと。

---

## 4. 残る穴（ガードが効かない経路）

- ラッパーを通さずに開発サーバーやテストランナーを直接起動した場合は、何も検査されない。
  **だからブリーフには直接起動の手順を書かない**
- 起動時刻の粒度（多くの OS で 1 秒）より速く PID が再利用されると、同一性の判定をすり抜けうる
- 指紋の対象から漏れたファイルの変更は検出できない。新しい設定ファイルを足したら対象に加える

ガード自身の空振り検査（素性判定を恒真にした写しでは「他人のサーバーを止める」が通ってしまうこと）は、
`docs/agents/quality-gates-shared.md` §1 の自己テストとして持つ。
