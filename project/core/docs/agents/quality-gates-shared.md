# Generator / Evaluator 共通の品質ゲート規約（唯一の置き場所）

> generator / evaluator の定義と CLAUDE.md は、この文書を**参照**し、内容を書き写さないこと。
> 同じ表を複数箇所に書き写すと、1 つの誤りが写した数だけ伝播する。
> スタック固有の規約（マイグレーションの採番・SQL 関数の後勝ちなど）は
> CLAUDE.md の「スタック: <名前>」節とその部品の文書が正。

## §1. 新しいガードには「空振りしていない標本」を添える

**ガード（テスト / lint ルール / CI チェック / 検査スクリプト / 自己テスト）を追加するときは、
そのガードが空振りしていないことを示す標本を必ず添える。**
「ガード」は、壊れたときに赤くなることで価値を出すもの全部を指す。

### なぜ必要か

ガードは普段すべて緑になる。出力上、次の 2 つは区別できない。

- 「検査した結果、問題が無かった」
- 「そもそも 1 度も実行されていない / 失敗を握り潰している」

CI のどのジョブからも呼ばれていないテストは、何スプリントでも「緑」を出し続ける。

### 標本の定義

**標本 = そのガードが必ず落とすべき入力。** 次の 2 点を、**同じ PR の中で、実行結果として**示す。

1. **ガードが有効なとき、標本は落ちる**
2. **ガードを無効化すると、標本は通ってしまう**（＝その赤はガード由来）

1 だけでは足りない。標本が接続エラーや構文エラーで落ちていても 1 は満たせてしまう。

### 2 つの流儀（どちらかに寄せる。新方式を発明しない）

| 方式 | 使いどころ |
|---|---|
| **標本ファイルを置く**（`*.probe.*`） | ガードが「実行環境ごと死ぬ」ことがある場合。**本番の実行経路で標本を毎回走らせ、落ちなければジョブを落とす** |
| **自己テストスクリプトを置く**（`scripts/selftest-*.sh`） | ガードの論理を、一時コピーを壊しながら検査できる場合。**リポジトリの実ファイルには書き込まない** |

標本ファイルの冒頭には「このファイルを直さないこと」と書く（直すと空振り検査が成立しなくなる）。

### Generator の手順

1. ガード本体を実装する
2. 標本または自己テストを足す
3. CI で走らせるなら、ワークフローと検査一覧を**同じ PR で**直す
4. **PR 本文に「ガードを無効化したら標本が通ってしまう」実測を貼る**

標本を添えられないなら、**そのガードを足さない。** 空振りか分からないガードは緑を 1 つ増やすだけで、
「1 failed なら想定内」という読み飛ばしを助長する。

### Evaluator の差し戻し条件

- 新しいガードがあるのに、標本も自己テストも無い
- 標本はあるが、本番の実行経路から呼ばれていない（置いてあるだけ）
- 「無効化したら通る」の実測が無く、手元でも再現できない

**Generator の申告を鵜呑みにせず、自分の手で 1 回ガード本体を壊して赤くなることを確認する。**

### 適用範囲

- **既存のガードに触れる PR も、その範囲で §1 を後追いで満たす。**「既存だから免除」ではない
- **計測装置・変異装置・起動スクリプト自身も対象。** これらが嘘をつくと他の全テストの緑が無意味になるため、
  通常のガードより優先度が高い（装置を故意に壊した入力で赤を返す「メタ標本」を持つ）

## §2. 外部の実態は推測せず照会する

スキーマ・関数定義・外部サービスの設定を変更・修正するときは、**推測で判断せず実態を照会する。**
Generator は実装時に、Evaluator はレビュー時に、それぞれ独立に確認する
（Generator が「その列は存在しない」と主張しても、Evaluator は鵜呑みにしない）。

| 推測しがちなこと | 照会の仕方 |
|---|---|
| 「エラーが出たから列が無い」 | DB のカタログ（`information_schema` 等）を引く |
| 「同名の関数は 1 つ」 | オーバーロードを列挙する（同名が共存すると呼び出しが解決できない） |
| 「コードと戻り値の形は合っている」 | 戻り値のキーと型定義を双方向に突き合わせる |
| 「外部サービスはこう設定されている」 | 管理 API / ダッシュボードで現在値を読む（購読イベント・宛先・鍵の所属先） |

スタック固有の照会クエリは、その部品の文書にある。

## §3. スコープ外の発見・非ブロッカー指摘は Issue に起票する

実装中・レビュー中に見つけたスコープ外の問題は、黙って見送らず Issue を起票する。
**コード・コミットメッセージ・レビュー本文に書くだけでは、マージした時点で事実上消える。**

### 起票する / しない

| 起票する | 起票しない |
|---|---|
| スコープ外だが修正が必要な欠陥（既存バグ・設計上の負債） | 好み・様式の話で、実害を説明できないもの |
| 重複管理・写経（同じロジック・定数が複数箇所にある） | すでに同じ Issue があるもの（下記の重複確認） |
| テストの空振り（変異で死なない・対象 0 件でも緑） | この PR の中で直す / 直させるもの |
| dev HEAD にも存在する既存の問題（「この PR 起因ではない」で終わらせない） | |
| ドキュメントと実装の不一致 / 同じ事故を繰り返す構造 | |

### 重複確認（新規起票の前に必ず行う）

**新しい番号を作るのは最後の手段。**

1. **閉じた Issue も検索する。** `gh issue list --state all --search "<語>"`。
   「今は直さない」で閉じた Issue の欠陥は残っている。主題そのものなら reopen して実測をコメントする。
   `completed` で閉じたのに残っているなら、それ自体が重要な発見
2. **最低 3 つの軸で引く:** ファイル名（最も外れにくい）/ 関数・シンボル名 / 現象の要点
3. **統合の形を選び、理由を書く:**

| 状況 | やること |
|---|---|
| 同じ根本原因・同じ範囲 | 既存にコメントで追記。新規起票しない |
| 新しい発見が既存の上位互換 | 既存のタイトルと本文を更新して範囲を広げる（元の本文は消さず「追記」の節を足す。タイトルが古いと次の人がまた別番号を作る） |
| 同じファイルだが根本原因が別 | 新規起票してよい。双方に相互リンクと違いを書く |

一部だけ直っている既存 Issue を見つけたら、残りに絞って本文を書き直す。

### Issue 本文の必須事項

- 事実・実測値・再現手順・`ファイル名:行番号`。「気になった」ではなく「こう壊れる」
- どの Issue / PR / レビューで発見したか
- なぜこの PR で直さなかったか（Generator は同じ理由を PR 本文にも書く）
- 踏みやすい罠があれば明記する
- 回帰で守るべき既存挙動。**Tier は書かない**（`docs/verification-tiers.md` §3）

### 起票後

- Generator: 起票番号を PR 本文の「起票した Issue」節に列挙する
- Evaluator: 起票番号をレビュー本文の「起票した Issue」節と完了報告に列挙する

## §4. 計測・変異・起動の装置を額面で信じない

**「緑」「SURVIVED」「exit 0」は、それを出した装置が正しく動いているときにだけ意味を持つ。**
装置に既知の嘘つき経路が見つかったら、下の表に行を足して Issue を起票する。
**行がある間は、その読みを額面で受け取らず、クロスチェックを併用する。**

| 装置 / 読み | 嘘つき経路 | クロスチェック | 直るまでの Issue |
|---|---|---|---|
| （初期状態では無し） | — | — | — |

- 装置は個別の PR（Generator 経由）で直し、§1 のメタ標本（装置を壊すと赤を返す実測）を添える
- **直った行は削除する**（残すと「まだ壊れている」と誤読される）
