# LINE（LIFF / LINE ログイン / Messaging API）の作法と教訓

> **この文書が唯一の置き場所（詳説）。** 規則の要約は CLAUDE.md の「スタック: line-liff」節。
> LINE の料金・上限・SDK の挙動は変わる。**初期化時と SDK 更新時に公式ドキュメントと `node_modules` の実装で確かめ直す。**

---

## 1. LIFF の認証（LINE ログイン + PKCE）

### 1-1. 何が起きうるか

`liff.login()` は PKCE の `code_verifier` を生成して Web Storage に保存し、LINE の認可画面へ遷移する。
戻ってきた callback で verifier を読み、認可コードと一緒にトークン交換する。

- SDK は **LIFF ブラウザ内では sessionStorage、外部ブラウザでは localStorage** に書き分けることがある
  （SDK のバージョンで変わる。更新時は `node_modules` の実装を読んで確かめる）
- **一部のアプリ内ブラウザは、認可のリダイレクトを往復する間に Web Storage の書き込みを保持しない。**
  callback で verifier が取れず、トークン交換が `invalid_grant`（verifier 不一致）で失敗する
- 失敗時に再ログインへ送ると、**また失敗 → また再ログイン の無限ループ**になる
- 増幅器: ログイン後の戻り先（`redirectUri`）に、前回の戻り先がそのまま入れ子で積み重なり、URL が再帰的に肥大する

### 1-2. 対策（全部入れる）

| 対策 | 要点 |
|---|---|
| **`liff.login()` の入口を 1 関数にまとめる** | 直接呼び出しを lint（`no-restricted-syntax` 等）で機械的に禁止する。以下の対策はすべてこの関数に入れる |
| **verifier を短命の cookie にミラーする** | SDK の書き込みは同期なので、`liff.login()` の呼び出し中だけ `Storage.prototype.setItem` を一時的に横取りし、**同じ同期実行の中で** cookie に複製する（ポーリングは遷移に負ける）。finally で必ず元に戻し、戻した後に両ストレージを読み直して取りこぼしを拾う |
| cookie の性質 | callback の JS が読むので `HttpOnly` にできない。verifier 単体は認可コード無しでは無価値なので、**TTL 10 分程度 + 使用後即削除**で露出を最小にする。https のときだけ `Secure` |
| **ミラーが失敗しても `liff.login()` は必ず実行する** | ミラーは緩和策。無くても従来の動作に戻るだけにする |
| callback の verifier 解決順 | localStorage → sessionStorage → cookie の順に探す |
| **`redirectUri` を毎回サニタイズして明示指定する** | 認証用のパラメータ（`code` / `state` / `liff.state` など）を落とし、戻り先パラメータの入れ子を剥がす。同一オリジンの相対パスだけを許す（オープンリダイレクト防止） |
| **失敗時は目的地（戻り先）に着地させる** | エラーページやホームに固定しない。利用者は少なくとも未ログインの状態で目的の画面を見られ、ループもしない |
| **callback を冪等にする** | React の StrictMode などで effect が 2 回走ると、同じ認可コードの交換が 2 回飛び、2 回目が失敗して遷移が二重発火する。1 回だけ実行するガードを置く |
| URL の後片づけは denylist で | ログイン後に URL から認証用パラメータだけを消す（必要なパラメータまで消さない）。処理は 1 関数に集約する |

### 1-3. 恒久的なクライアント診断

**アプリ内ブラウザの不具合は手元で再現できない。** 本番で観測できる診断ログを常設する。

- ログイン開始（attempt）と結果（result）を 1 行ずつ、サーバーの監査ログに送る
- 載せるもの: 結果・失敗理由の分類・**verifier をどこから取れたか（local / session / cookie / なし）**・UA の要約・入れ子の深さ
- **載せないもの: verifier・認可コード・トークン・個人情報**
- 仮説を切り分けるための一時的なフラグ（例: verifier を意図的に落とす）は、**本番ビルドでは構造的に無効**にする

### 1-4. ログインの位置（「先にログイン」を既定にする理由）

- 予約・購入などのフローで、**ログインを最後（確定時）まで後ろ倒しにする案は採らない**のを既定とする
- 理由: 選択の途中で LINE ログインに出ると、**元の画面と途中の状態に戻すのが難しい**（戻り先の URL・フォームの状態・
  1-1 の verifier 問題が重なり、考慮すべきパターンが一気に増える）
- 離脱が気になるときは、ログインの「位置」ではなく「見せ方」で改善する（文言・次の画面の予告・LINE の同意画面の設定）
- 効果はログイン段の計測（ボタン押下 → ログイン完了）で確かめる
- 後ろ倒しを検討するなら、状態の保存と復元・1-2 の全対策を前提に ADR で決める

### 1-5. 友だち追加オプションとスコープ

| 設定 | 選択肢 | 判断の軸 |
|---|---|---|
| 友だち追加オプション（LINE ログインチャネルの設定 / `bot_prompt`） | normal: 同意画面に「友だち追加」のチェックを出す / aggressive: 同意の後に友だち追加の画面を別に出す | aggressive は友だちが増えやすいが、**画面が 1 枚増えて離脱が増えうる**。通知を届けることが価値の中心なら aggressive、ログインの摩擦を最小にしたいなら normal。**友だちでない相手には push が届かない**ことを前提に決め、決めた理由を ADR に残す |
| スコープ | `openid` / `profile` から始める | **必要最小限にする。** スコープが増えると同意画面の項目が増える。`email` は申請・審査が要る |

### 1-6. 開発時の確かめ方

| 確かめたいもの | 方法 |
|---|---|
| UI | ローカル（LIFF のモック）で高速に |
| LIFF・ログイン・Messaging API | トンネル（ngrok 等）+ **stg 用のチャネル**で実機。本番チャネルを開発に使わない |
| 本番前の統合 | staging（プレビュー環境）で実機 |

アプリ内ブラウザの挙動は OS と LINE のバージョンで変わる。認証まわりの修正は R3（staging 先行の選択リリース）で出す。

## 2. Messaging API の料金と上限

### 2-1. 何が数に入るか

| 送り方 | 数に入るか |
|---|---|
| **応答メッセージ**（webhook の reply token で返す） | **入らない（無料）** |
| push / multicast / broadcast / narrowcast | **入る** |

- 料金プランは月の送信上限と、**上限を超えたときに追加購入できるか**で分かれる
- **追加購入できないプランでは、上限に達するとその月の push 系は全部止まる。** 予約確定・リマインダーのような
  重要な通知も一緒に止まる（応答メッセージは止まらない）
- プラン・上限・単価は変わる。**初期化時に公式で確かめ、`docs/bootstrap.md` の「外部サービスの上限」表に
  「上限を超えたら何が起きるか」まで記録する**

### 2-2. 監視とブレーカー

- 当月の上限と消費数を API（`/v2/bot/message/quota` と `/v2/bot/message/quota/consumption`）で**毎日**取得し、時系列に残す
- **消費率が閾値（例 80%）を超えたら運用者に警告する**（運用通知の即応チャンネル）
- **ブレーカー**: 送信の種類に優先度を付け、残りが少なくなったら低優先度（ダイジェスト・お知らせ）から止めて、
  重要な通知（予約確定・キャンセル・リマインダー）に枠を残す。止めたことはログに残す
- 送信数は「事業主の数 × 顧客の数 × 通知の種類」で増える。新しい通知を足す PR では、月の送信数の見積もりを書く

### 2-3. 事業者側への通知は既定でまとめる

マルチテナントで事業者（店舗・スタッフ）にも LINE で知らせる場合:

- **既定は「1 件ごとのリアルタイム push をしない」。** 1 日 1 回のまとめ（日次サマリー）で届ける。
  理由: 通知疲れ（1 日数十件の通知は読まれなくなる）と送信枠の消費（事業者 × 件数で増える）
- 顧客向けのリアルタイム通知（確定・キャンセル・リマインダー）は別。顧客は管理画面を見に来られない
- リアルタイムが必要な事業者には**事業者ごとの opt-in** にし、次を必ず付ける:

| 仕掛け | 要点 |
|---|---|
| まとめ（coalescing） | 同じ宛先への通知を一定時間（例 15 分）に 1 回へまとめる。「この時間枠を取った」を DB で原子的に確保する（compare-and-set） |
| 上限（cap） | 宛先ごとに 1 日の上限を設ける |
| 落とした通知を失わない | 本文は「いまの未処理件数」を書き、ボタンは一覧（または最も近い 1 件）を開く。1 通で溜まった分を片づけられるようにする |
| 宛先の重複排除 | 同じ人が複数の役割を持つときに 2 通届けない（ユーザー ID と LINE のユーザー ID の両方で重複を除く） |

この方針を変えるときは ADR を足す。

## 3. Flex Message の構成はプロジェクトの規約

- **通知の種類ごとの構成（ボタンの数・文言・遷移先）は、要件ドキュメントの表を唯一の正とする。**
  実装者・エージェントが「便利そうだから」とボタンを足さない（通知の意味が種類ごとにぶれ、テストの期待値も割れる）
- 表と実装を意図的に違えている箇所があれば、要件ドキュメント側にその旨を書く（要件を根拠に実装を「直さない」ため）
- Flex の JSON はテンプレート関数に集約し、種類ごとに構成のスナップショットテストを置く
- 代替テキスト（`altText`）は通知一覧に出る。種類ごとに中身が分かる文にする
