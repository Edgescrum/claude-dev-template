## スタック: line-liff

LINE 公式アカウントを入口にし、LIFF（LINE 内ブラウザのアプリ）・LINE ログイン・Messaging API を使う。
詳説と経緯は **`docs/line-liff.md`（唯一の置き場所）**。LINE の料金・上限・SDK の挙動は変わるので、
**初期化時と SDK 更新時に公式ドキュメントと `node_modules` の実装で確かめ直す。**

プロジェクト固有の構成（記入）:

| 項目 | 値 |
|---|---|
| 公式アカウントの数と分け方 | （例: 全テナント共通で 1 つ。テナントは URL パラメータで識別） |
| チャネル | 本番 / stg の LINE ログイン・Messaging API チャネル（開発は stg を使う） |
| 認証 | （例: LINE ログインのみ。メール / パスワードなし） |
| 友だち追加オプション | normal / aggressive（理由は ADR） |
| Messaging API のプランと上限 | `docs/bootstrap.md` の「外部サービスの上限」表 |

### LIFF の認証

| 規則 | なぜ |
|---|---|
| **`liff.login()` は 1 つのラッパー関数からだけ呼ぶ**（直接呼び出しは lint で禁止） | 下の対策を全経路に効かせるため |
| PKCE の `code_verifier` を**短命の cookie にミラー**し、callback では localStorage → sessionStorage → cookie の順に探す | 一部のアプリ内ブラウザは認可のリダイレクト往復で Web Storage を失い、トークン交換が毎回失敗する |
| ミラーが失敗しても `liff.login()` は必ず実行する | ミラーは緩和策。壊れても従来動作に戻るだけにする |
| **`redirectUri` は毎回サニタイズして明示指定する**（認証パラメータを落とす・戻り先の入れ子を剥がす・同一オリジンの相対パスだけ） | 戻り先が再帰的に入れ子になり、失敗ループを増幅する |
| **失敗時は目的地に着地させる**（エラーページ・ホームに固定しない） | ループを断ち、利用者は目的の画面を見られる |
| callback は冪等にする（同じ認可コードを 2 回交換しない） | effect の二重実行で 2 回目が失敗し、遷移が二重発火する |
| **ログインの attempt / result を本番の監査ログに常設する**（verifier の取得元は載せ、verifier・コード・トークン・個人情報は載せない） | アプリ内ブラウザの不具合は手元で再現できない |
| 認証まわりの修正は staging で実機確認してから本番に出す（`release-and-hotfix.md` の R3） | OS と LINE のバージョンで挙動が変わる |

### ログインの位置とスコープ

- **フローの途中・最後までログインを後ろ倒しにしないのを既定とする。** LINE ログインの往復の後に元の画面と途中の状態を
  復元するのは難しく、考慮すべき組み合わせが一気に増える。離脱対策は「見せ方」（文言・次の画面の予告・同意画面の設定）で行い、
  ログイン段の計測（押下 → 完了）で確かめる
- スコープは `openid` / `profile` から始め、**必要最小限**にする（同意画面の項目が増えると離脱が増える）
- 友だち追加オプションは「通知を届けることが価値の中心か」で normal / aggressive を選び、ADR に残す。**友だちでない相手には push が届かない**

### Messaging API の送信枠

| 規則 | なぜ |
|---|---|
| **応答メッセージ（reply token）だけが無料。push / multicast / broadcast / narrowcast は枠を消費する** | 送り方で費用が変わる |
| **追加購入できないプランでは、上限に達するとその月の push が全部止まる**（重要な通知も一緒に） | 「料金が増える」ではなく「止まる」 |
| 当月の上限と消費数を API で毎日取得して残し、閾値（例 80%）超えで運用者に警告する | 止まる前に気づく |
| 送信に優先度を付け、残りが少なければ低優先度から止める（ブレーカー） | 重要な通知に枠を残す |
| 新しい push を足す PR では、月の送信数の見積もり（宛先数 × 頻度）を書く | 枠の消費は足し算で増える |
| 事業者側への通知は**既定で日次のまとめ**。リアルタイムは事業者ごとの opt-in にし、まとめ（時間窓）・1 日の上限・「いまの未処理件数」を載せる本文を必須にする | 通知疲れと送信枠の消費 |

### Flex Message

- **通知の種類ごとの構成（ボタンの数・文言・遷移先）は要件ドキュメントの表が規約。** 実装者・エージェントがボタンを足さない
- 要件と実装を意図的に違えている箇所は、要件ドキュメント側に明記する（要件を根拠に実装を「直さない」）
- Flex はテンプレート関数に集約し、種類ごとに構成のスナップショットテストを置く。`altText` は種類が分かる文にする

### Webhook

- 署名（`x-line-signature`）を**生のリクエストボディ**で検証してから処理する。検証できなければ何もしない
- follow / unfollow などの処理は、レスポンスを返す前に `await` する（ホスティング部品の規則も参照）
- 同じイベントが再送されうる前提で、冪等に処理する

### 開発時の確かめ方

UI はローカル（LIFF のモック）、LIFF・ログイン・送信はトンネル + **stg チャネル**で実機、本番前は staging で実機。
**本番チャネルを開発に使わない。**
