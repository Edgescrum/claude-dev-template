# 隔離 worktree でローカル DB スタックを使う（起動から**片づけまで**）

> **この文書が唯一の置き場所。** CLAUDE.md やエージェントのブリーフに書き写さないこと。
> 対象: Generator / Evaluator / Orchestrator、および隔離 worktree で作業する全員。
> ここに出てくる `db:*` のコマンド名は**ラッパーの規約名**。実装はプロジェクトの初期化（`docs/bootstrap.md` 0-5）で
> 用意する（雛形に実体は無い）。ラッパーが満たすべき要件は §3。

---

## 0. 結論だけ先に

```bash
cd <隔離 worktree>
<INSTALL_CMD>

npm run db:isolate                  # ① config.toml を自分専用に採番する（1 回だけ）
npm run db:start                    # ② 起動（起動時の素性を supabase/.stack-id に記録する）
npm run env:localdb                 # ③ .env.local を config.toml のポートから作る

# … 作業 …
npm run db:reset                    # マイグレーション全適用 + seed
npm run db-tests                    # DB テスト

# 片づけ（事故が起きやすい局面）
npm run db:stop -- --volumes        # ④ 自分のスタックだけを止めて volume も消す
git checkout supabase/config.toml   # ⑤ 必ず stop の「後」。順序を逆にしない
```

**`supabase` CLI を直接打たないこと。とくに `supabase stop` は使わない（理由は §2）。**

### 片づけは義務

- 作業が終わったら、**成否に関わらず報告を書く前に** `db:stop -- --volumes` を実行する
- **`--volumes` を省略しない。** 既定で volume を残すため、省くと 1 スタックあたり数百 MB が積み上がる
- **立てないで済むなら立てない。** 何を検証するかで決める（下表）。起動と片づけで数分かかり、
  Generator と Evaluator が別々に立てるので往復で倍になる

| 検証したいもの | 隔離スタックは |
|---|---|
| DB テスト / マイグレーションの適用確認 | `supabase/**` に差分が無いなら不要 |
| e2e / ブラウザでの実測 | **要る**（`supabase/**` の差分とは無関係。e2e もアプリも DB 無しでは動かない） |

同時実行数の上限は `docs/agents/agent-dev-server.md` §0 が正。

---

## 1. 典型的な事故の形

隔離は正しくできていても、**片づけの順序**で壊れる。

```bash
git checkout supabase/config.toml            # project_id が運用者のものに戻る
supabase stop --workdir <隔離 worktree> --no-backup
# → CLI は --workdir ではなく「戻したばかりの config.toml」の project_id を読む
# → 運用者のコンテナを停止・削除し、--no-backup なので volume も削除する
```

運用者の手動テスト用データは、バックアップに無ければ復元できない。

---

## 2. 3 つの不変条件

### 2-1. `--workdir` はガードではない

`--workdir` は「どの config を読むか」でしかなく、「さっき自分が起動したスタック」を指さない。
**信頼の根拠に使えるのは、CLI が起動時にコンテナへ付けるラベルだけ**
（`com.supabase.cli.project` / `com.supabase.cli.workdir`）。
「いまいる worktree のスタックか」の判定は 1 本のスクリプトにまとめ、**別の場所に書き直さない**（ずれた瞬間に片方が空振りする）。

### 2-2. 停止は「起動したときの project_id」を覚えていない

起動と停止の間に `config.toml` は普通に変わる（commit 前に戻す・ブランチ切り替え・コンフリクト解消）。
だから**起動時に自分で記録する**。`db:start` は `supabase/.stack-id`（gitignore 対象）に
`project_id` / `workdir` / ポートを書き、`db:stop` はこの記録を正として対象を決め、
**その上で**コンテナのラベルがこの worktree を指しているかを検査してから、`docker rm -f` を名指しで実行する。

### 2-3. `--no-backup` は「停止」ではなく「破棄」

`supabase stop --no-backup` は volume ごと消す。`db:stop` は**既定で volume を残し**、
消すときだけ `--volumes` を明示させる。`--no-backup` は受け付けない。

## 3. ラッパーの要件（実装するときの仕様）

| 経路 | 要件 |
|---|---|
| `db:isolate` | worktree 名から project_id とポート帯を決定論的に採番する。その帯を別 worktree のスタックが使っていたら次の空き帯へずらし、ずらしたことを表示する |
| `db:start` | 共有 config のままの隔離 worktree では起動しない。起動後に `.stack-id` を記録する |
| `db:stop` | `.stack-id` を正とし、コンテナのラベルを検査してから名指しで削除する。**他人のスタックの削除は、どの逃げ道でも許さない** |
| `db:reset` / `db-tests` / `db:push` | 接続先が自分の worktree のスタックでなければ、`supabase` を呼ばず・1 本も実行せずに `exit 2` |
| `dev`（アプリの起動） | `.env.local` が他人のローカルスタックを指していたら起動しない |
| `seed:*` | 本番拒否 + 接続先の素性検査。**判定の実装は 1 本だけ**にして、すべての seed から呼ぶ |
| `env:localdb` | ポートを `config.toml` から埋める（テンプレートの既定ポートを焼き付けない） |
| `db-target` | いま何に向いているかを表示する |

- docker が使えず素性を引けない環境では、CI のときだけ警告して続行し、それ以外は拒否する（fail-closed）
- 「検証済み」をシェルの環境変数で短絡するなら、**その記録の worktree がいまの worktree と一致するときだけ**効かせる
  （1 度検証したシェルで別 worktree に `cd` して書き込めてしまう）
- 自己テストで、**素性判定を恒真に書き換えた写しでは「他人のスタックを止める」「他人の DB を reset する」が通ってしまう**ことまで確かめる
  （`docs/agents/quality-gates-shared.md` §1）
- seed スクリプトは、判定関数のテストだけでなく「**`main()` からガードが呼ばれていること**」を実プロセスで確かめる。
  純粋関数のテストは、呼び出しを消しても緑のまま

### 残る穴

- **`supabase` / `docker` を直接打つ経路は全部止められない。** ラッパーは「使ってくれたとき」だけ効く。
  だから CLAUDE.md とブリーフには直接呼び出しの手順を書かない
- 逃げ道の環境変数（素性検査を飛ばす類）は、**読み取り専用の用途と書き込みの用途で別の変数**にする。
  1 つにまとめると「見るだけ」のつもりで書き込みが通る

## 4. 隔離 worktree からブラウザで実測したいとき

**「実ブラウザで確認せよ」と「他人の DB に近づくな」は両立する。**

1. **第一候補: 自分のスタックを立てる。** `db:isolate` → `db:start` → `env:localdb` → 必要な seed → アプリを起動。
   ブリーフが禁じているのは **`supabase` の直接呼び出し**であって、**`db:*` のラッパーは禁止されていない**
2. **立てない場合の正規の逃げ道: 読み取り専用で運用者のスタックに繋ぐ。**
   アプリ起動時の検査を「拒否」から「警告して続行」に落とす専用の変数を使い、**警告がログに残る形**で起動する。
   - 書き込みを伴う操作をしない（作成・保存・seed は禁止。GET で完結するものだけ）
   - `db:reset` / `seed:*` / `db:stop` は打たない
   - 作業後、運用者のデータが変わっていないことを軽く確かめて PR に書く
3. ❌ **`.env.local` をコピーしてアプリを直接起動しない。** 検査を通らないので、
   「他人の DB に繋いだ」事実がログから消え、何を見たのか後から再現できない

---

## 5. 運用者のローカル DB を壊してしまったとき

1. `npm run db:start` でスタックを作り直す（マイグレーションの適用まで走る）
2. 手動テスト用のシードを順に流し直す（どの seed をどの順で流すかは CLAUDE.md の「スタック: supabase」節に書いておく）
3. 失ったデータと原因を Issue に記録する

seed には「既存の行を消さず不足分だけ足す」型と「シードした行のうち今回の定義に無いものを消す」型がある。
**どちらの型かを seed ごとに明記し、消す型には消さない逃げ道（環境変数）を用意する。**
