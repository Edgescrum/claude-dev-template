# design-variants — UI 案の発散と Figma への翻訳

UI 確定フローの正は `docs/ui-confirmation-flow.md`。本スキルはそのステップ 1.5（参照収集）〜5（乖離裁定の準備）と
7（Issue 下書き）を実行する。プロダクト固有の値（画面の幅・ブランド色・言語・カタログ URL）は
CLAUDE.md の「スタック: ui-figma-ds」節を読む。以下の「§」は `docs/ui-confirmation-flow.md` の節番号。

| 使う値 | どこにあるか |
|---|---|
| 画面モックのファイル（Screen） | file key `{{FIGMA_SCREEN_FILE_KEY}}` |
| DS ライブラリ | file key `{{FIGMA_LIBRARY_FILE_KEY}}` |
| 画像生成の API キー | リポジトリ外のローカル env ファイル（例: `~/.config/design-variants/.env` の `OPENAI_API_KEY`） |
| 共通コンテキスト・カタログ URL | CLAUDE.md の「スタック: ui-figma-ds」節 |

## 前提の確認（最初にやる）

1. この変更は `docs/ui-confirmation-flow.md` §1 のしきい値で**フロー必須**か？
   （文言・既存パターンの踏襲なら本スキルは不要。Issue に「Figma 対象外（理由）」と書いて通常フローへ）
2. grill でデータ契約が確定しているか？ 未確定なら先に grill（バック Issue の先行起票まで）
3. 対象画面の実際のデータ型（サーバー処理の戻り値）を確認し、**現実的なフィクスチャ**（0 件・多数件・最長文字列）を用意する。
   画像に実在しないデータを描くと、翻訳時まで発覚しない
4. シェルを使うプロジェクトなら、§8 の決定表で**どのシェルの上に描くか**を先に決める
5. Figma を操作する前に、Figma プラグインのスキル（`figma-use` / `figma-generate-design` 等）を**必ず先にロード**する。
   Figma の運用（ステータス・ハンドオフ）で迷ったら `figma-docs-first` で公式ヘルプを確かめる

## ステップ 0.5: 参照収集（Mobbin・§7）

目的は**動線と UI 要素の参考**（色・装飾などの見た目は写さない）。Mobbin のツール
（`search_flows` / `search_screens` / `search_sections`）を使う。ツールが無いセッションでは「参照なし」で先へ進んでよい。

1. **検索語を作る。** 対象画面の作業を一般アプリの言葉に置き換える（業種名では引かない）

   | 作業 | 検索語の例 |
   |---|---|
   | 休みの登録 | mark days as unavailable / block time in a calendar |
   | 代理の登録 | create an appointment on behalf of someone |
   | ダッシュボード | home screen showing today's schedule at a glance |
   | 初期設定 | setup checklist onboarding |
   | 予約 | book an appointment: choose service, pick date and time |

   分析で詰まりどころが分かっているなら、それを起点にする
2. **引く。** 複数画面の流れはフロー検索（3〜4 件）、1 画面は画面検索（6〜10 件）。スマホ画面は `platform: ios`。
   各呼び出しの `output_destination` / `task_intent` は同じタスク内で揃える
3. **参照ボードを作る。** 5〜10 件。**動線と UI 要素を分けて**抜き出し、各件に「何の問題を解いているか」
   「こちらのどの詰まりに当たるか」「動作環境の制約に反しないか」を書く。引用は `mobbin_url`（画像 URL は失効する）。
   `ai_usage_notice` が返ったら原文のまま運用者に見せる
4. **パターンを案に割り当てる。** 案ごとに 1 パターン。**最低 1 案は参照なし**。参照の選定は Claude が行い、運用者に別途の裁定を求めない

## ステップ 1: 発散（3〜5 案の画像生成）

### 経路 A（既定）: 画像生成 API

- API キーはリポジトリ外のローカル env ファイルから読む（**リポジトリ・ホスティング・Issue に置かない**）
- 全案共通のコンテキストを固定で注入した上で、案ごとに異なるアートディレクション（情報密度・レイアウト型・トーン）を与える

```
共通コンテキスト（毎回入れる。中身は CLAUDE.md の「スタック: ui-figma-ds」節）:
  <デバイスと幅（例: 390px のスマホ画面）>
  <プロダクトの種類と利用者>
  <UI の言語>
  <ブランドの色と雰囲気>
  Realistic data: <用意したフィクスチャの内容>
```

- ステップ 0.5 で割り当てたパターンは、**構造と動線を言葉で**指示に入れる
  （例:「カレンダーで日付を複数タップで選び、下から出るシートの 1 ボタンでまとめてブロックする」）。
  **Mobbin の画像を参照画像として渡さない**（他社アプリの見た目に寄るため）
- 既存画面の改修なら、現画面のスクリーンショットを参照画像として渡す（image edit）
- 縦長のサイズで生成する。1 機能あたりのコストは小さい（再生成をためらわない）

### 経路 B（費用ゼロ）: 自由描画

機能を持たない HTML / SVG を「絵」として描き（DS に縛らない。表現優先）、ブラウザ自動操作でスクリーンショットを撮る。
鍵が無い・費用ゼロ指定のときに使う。

### 提示

生成した案をスクラッチディレクトリに保存し、横並びの比較ページ（1 枚の HTML）にして運用者に見せる。
各案のラベルに参照元（Mobbin のリンク / 「参照なし」）を書く。**選定は運用者。** 落選案は破棄する（保管しない）。

## ステップ 2: 翻訳（構造分解 → Figma 化）

1. 採用画像を部位ごとに分解し、対応表を作る

   | 部位 | 分類 | 参照 |
   |---|---|---|
   | 一覧のカード | 既存 `Card` | — |
   | 絞り込みチップ | `Badge` の variant 追加（★DS Issue 候補） | Mobbin の画面リンク |
   | 進捗リング | ★新部品候補 | Mobbin の画面リンク |
   | 売上の推移 | ★新データ要求（現在のデータ契約に無い → バック Issue） | — |

   DS のカタログと見比べて既存部品で表現できるかを判断し、できなければ ★variant 追加 / ★新部品候補 に分類する。
   ボードに無い部位で迷ったら、その部位だけ画面検索で引き直す
2. DS ライブラリ（`{{FIGMA_LIBRARY_FILE_KEY}}`）の部品と Variables を使い、Screen ファイル（`{{FIGMA_SCREEN_FILE_KEY}}`）に組む。
   シェルを使うなら、そのテンプレートを複製してから組む。
   画像から持ち込むのは**レイアウト構造・情報の優先度・表現の意図**だけ。色 / 余白 / 角丸 / 影はトークンにスナップする（画像の値を測って写さない）
3. **乖離リスト**（画像にあったが Figma で消えた表現）を作り、運用者に裁定を仰ぐ:
   捨てる / 既存部品で近似 / 新部品として DS へ（→ DS 側に Issue。DS 先行原則・§4）
4. ★新データ要求があれば、バック Issue をこの時点で起票する

## ステップ 3: 確定待ち → Issue 下書き

運用者が Figma で微修正 → 状態チェックリスト（§3）→ フレームを **Mark as ready for dev** したら、フロント Issue を起票する。必須記載:

- `Figma: <確定フレームのノード URL>`
- 採用画像（添付）と乖離裁定の一覧（意図的に画像から変えた点）
- 参照ボード（Mobbin のリンクと、採用案に効いたパターン）
- 状態の扱い（描いたフレーム or 「〜は既存パターン踏襲」の宣言）
- 使う DS 部品の一覧（新部品は DS の該当バージョンを明記）
- Evaluator の照合観点は §6（4 点 + 視覚メモ）であること

## やってはいけないこと

- 選定・乖離裁定・確定を、運用者を待たずに進める（3 つとも運用者の裁定ポイント）
- 画像の色や余白を Figma / コードに測って写す（トークン外の直書きの発生源）
- DS に無い部品をプロダクト側に先行実装する（例外条件と `ds-debt` の義務は §4）
- API キーをリポジトリ・ホスティング・Issue に書く
- Mobbin の画像を画像生成の参照画像に渡す / 画像 URL を Issue に貼る（失効する）
- 確定の印にセクション移動などの独自規約を使う（ネイティブの ready for dev を使う）
