# UI 確定フロー（実装前に Figma で確定させる）

> **この文書が UI 確定フローの唯一の置き場所。** 実行は `/design-variants` スキル（`.claude/skills/design-variants/SKILL.md`）。
> 目的: フロントの新規・変更の見た目を Generator / Evaluator の即興に任せない。
> 「後から細かな修正が続く」原因 3 つを、それぞれ次で潰す。
>
> | 原因 | 潰し方 |
> |---|---|
> | 視覚の裁量が実装者にある | 運用者が画像案から**選定**する（§2） |
> | 状態が未定義 | **状態チェックリスト**（§3） |
> | Evaluator に正解の見た目が無い | Figma の確定フレームとの**4 点照合**（§6） |

---

## 0. 新規プロジェクトの最初: デザインの土台（Phase D）

新規プロジェクトには、UI 確定フローが「当てはめる先」にする DS（デザインシステム）がまだ無い。
そこで最初の 1 回だけ、**中核の動線のモックから DS の土台とプロトタイプを作る**。Planner の Phase 0（環境準備）とは並行で進める。

| # | 工程 | 担当 | 運用者の裁定 |
|---|---|---|---|
| D-1 | grill で詳細要件と**データ契約**（画面が読み書きするデータの形・認可）を確定し、要件ディレクトリに残す | Planner + 運用者 | 論点の裁定 |
| D-2 | **中核の動線だけ**を選び（例: 初回登録・主な作業・支払い。目安 3〜5 本）、本フローの 2〜3（参照収集 → 画像で発散 → 選定）でモックにする。**全画面は作らない** | UI / UX セッション | 案の選定 |
| D-3 | 選んだモックから **DS の土台**を作る: トークン（色・文字・余白・角丸・影）と中核の部品。Figma のライブラリとコードの両方に作り、対応付けを取る | UI / UX セッション | トークンと部品の確認 |
| D-4 | 中核の動線を Figma の **プロトタイプ**（画面遷移つき）にし、運用者が実際に触って動線を確かめる | UI / UX セッション | **動線の確認（新しい裁定ポイント）** |
| D-5 | 確かめたフレームを Mark as ready for dev にし、機能ごとの Issue に Figma の URL を付ける | UI / UX → Planner | — |

- **モックが先に渡された場合は D-2 を省く。** ただし渡されたモックには空状態・エラー・最長ケースがほぼ描かれていないので、本フロー §3 の状態チェックリストで洗い出してから D-3 に進む
- **実装は D-5 を待たない。** D-1 でデータ契約が決まれば、UI を含まない部分（データ・ロジック・API）は直後から着手できる。フロントとバックで工程を分けず、Issue は機能単位の縦切りにし、待ちが出る部分だけを別 Issue に切る
- **2 本目以降の機能は、D-3 で作った DS に当てはめる通常の本フロー（§2）で、着手の直前に作る。** 最初に全画面を作り込まない（序盤の学びで後半の前提が変わるため）

## 1. 適用しきい値

| 変更 | フロー |
|---|---|
| 新規画面・レイアウト変更・新しい表現の UI | **本フロー必須** |
| 文言・既存パターンの踏襲・微調整 | 対象外（Issue に「Figma 対象外（理由）」と 1 行書く） |

- フロント系の Issue は「`Figma: <ノード URL>`」か「`Figma 対象外（理由）`」の**どちらかを必須**とする。
  宣言は起票者が書き、**妥当性は Evaluator が検証する**（検証 Tier と同じ「申告 / 検算」の分離）
- **どのセッションでも「新しい画面を作って」「レイアウトを変えて」と言われたら、実装に入らず本フローに回す**

## 2. フロー本体

```
1.   grill: 要件 + データ契約（サーバー処理の型 / 返す列 / 認可）を確定
       → バック Issue を即起票（UI の反復を待たずに先行させる。2 レーンに分ける）
1.5  参照収集（§7）: Mobbin で「動線」と「UI 要素」の参考を引き、パターンとして抽出する
2.   発散: /design-variants で 3〜5 案を画像生成（DS に縛らない。シェルを使うなら、どのシェルの上に描くかは先に決める）
3.   選定: 運用者が 1 案を選ぶ。落選案は破棄する
       1.5 のパターンは案ごとに 1 つずつ割り当てる。**最低 1 案は参照なし**で描く
4.   翻訳: 画像 → 部位ごとに分解（既存 DS 部品 / variant 追加 / ★新部品候補 / ★新データ要求）
       → DS ライブラリの部品と Variables に**強制スナップ**して Figma 化
       （画像から持ち込むのはレイアウト構造・情報の優先度・表現の意図だけ。色 / 余白 / 角丸 / 影は持ち込まない）
5.   乖離裁定: 「画像にあったが Figma で消えた表現」を一覧にし、運用者が 1 件ずつ
       捨てる / 既存部品で近似 / 新部品として DS に追加（§4）を裁定する
       ★新データ要求はこの時点でバック Issue を追加起票する（マージ後に発覚するのが最悪）
       レビュー観点に「この UI はどんなクエリを生むか」（N+1・新しいインデックス・権限境界）を含める
6.   運用者が Figma で微修正 → 状態チェックリスト（§3）→ フレームを **Mark as ready for dev**
7.   フロント Issue 起票（Figma ノード URL + 採用画像 + 乖離裁定 + 参照ボード）→ Generator / Evaluator
```

**運用者が裁定するのは 3 点だけ: 画像の選定（3）・乖離の裁定（5）・確定（6 の ready for dev）。**
参照の選定や分解は Claude が行い、運用者の裁定ポイントを増やさない。

セッション分担: 2〜6（発散〜確定）は Strategy / UI・UX セッション、7 以降の実装は main セッション。
**main は Figma ノード URL 付きの Issue が存在して初めて着手する。**

## 3. 状態チェックリスト（確定の条件）

| 状態 | 確かめること |
|---|---|
| 空状態 | 0 件のとき何を出すか・次の行動への導線 |
| ローディング | 何が先に見えるか |
| エラー | 何を伝え、どう戻れるか |
| 最長ケース | 長い名前・多数のアイテム・折り返し |
| キーボード表示時（モバイル） | 確定ボタンが隠れないか |

**既存パターンの名前を書けるなら宣言でよい。書けないなら Figma で描く。**
（例:「空状態は既存の EmptyState を踏襲」→ フレーム不要。この画面固有の見た目がある状態だけ描く）

## 4. 新部品ゲート（DS 先行原則）

- モックが DS に無い部品 / variant を要求したら、**DS に先に追加**（DS 側の PR → リリース）してからプロダクトの実装に入る
- **例外は本番障害級の緊急だけ。** プロダクト側で先行したら **`ds-debt` ラベルの負債 Issue を同時に起票する（必須）**
- `ds-debt` は定期の解消ループ（週 1 のスケジュール実行）で走査し、DS への昇格 PR とプロダクト側の置換 Issue までを作る。
  DS の PR のマージは人が確認する

## 5. Figma ファイルの運用

- 画面モックは**ライブラリとは別の専用ファイル（Screen）**に置き、DS ライブラリをリンクする。ページ = 機能単位
- **確定の印は Dev Mode のネイティブ機能「Mark as ready for dev」**。セクションの移動などの擬似ステータスは使わない。
  利点: Ready だけを絞り込める / マーク後の変更が差分追跡される（「確定後に触ったら Issue を切り直す」を仕組みで検知できる）/
  REST API の `devStatus` で機械検証できる。実装がマージされたら **Completed** に進める
- 落選案・検討中のフレームはファイルに残さない（確定形の正 = Figma、経緯の正 = Issue）
- Figma の運用（ステータス・ハンドオフ・命名）を決める前に、**ネイティブ機能を公式ヘルプで確かめる**（ユーザーレベルのスキル `figma-docs-first`）

## 6. Evaluator の照合（4 点。違反だけが差し戻し理由）

1. 指定された DS 部品が使われているか（勝手な div 組みをしていないか）
2. レイアウト構造・情報の順序が Figma と一致するか
3. 宣言された状態（§3）が全部実装されているか
4. トークン外の直書きの色 / 余白が無いか

4 点を満たした上での美観の微差（数 px の余白感・改行位置）は差し戻し理由にせず、レビューに「視覚メモ」として列挙する。
微差の裁定は運用者が staging で行う。1 の判定には DS のカタログ（Storybook 等。URL は CLAUDE.md の「スタック: ui-figma-ds」節）を使う。

## 7. Mobbin による参照収集

目的は**動線と UI 要素の参考**。色・装飾などの見た目は写さない（見た目は DS のトークンで決まる）。
業務用の画面であっても、一般消費者向けアプリを参考にしてよい（同じレイアウトである必要はない）。

- **動線**: 作業の進み方。何画面で終わるか・どこで選ばせるか・まとめて操作できるか
- **UI 要素**: 1 つの操作を支える部品の使い方（例: 空きのある日に印が付くカレンダー / 横スクロールの日付の帯 / 「合うものがない」の逃げ道 / 画面下に固定された確定ボタン）

| 項目 | ルール |
|---|---|
| 検索の使い分け | 複数画面の流れ = フロー検索 / 1 画面 = 画面検索 / LP・ブログ = Web のセクション検索 |
| プラットフォーム | スマホの画面は iOS、PC 前提の画面と LP は Web |
| 検索語 | **業種名で引かず、作業を一般アプリの言葉に置き換える**（例: 休みの登録 → カレンダーで日付をブロック / 代理の登録 → 他の人の代わりに予定を作る / ダッシュボード → 今日の予定を一目で見る画面 / 初期設定 → セットアップのチェックリスト）。分析で詰まりどころが分かっていれば、それを起点にする |
| 出力 | **参照ボード**: 5〜10 件。**動線と UI 要素を分けて**抜き出し、各件に「何の問題を解いているか」「こちらのどの詰まりに当たるか」を書く |
| 引用 | **`mobbin_url` で行う。** 画像 URL は失効するので使わない |
| 画像生成への渡し方 | **Mobbin の画像は画像生成に渡さない。** 構造・動線を言葉にして渡す（他社アプリの見た目に寄った案を作らないため） |
| 発散の確保 | パターンは案ごとに 1 つ。**最低 1 案は参照なし**で無制約に描く |
| 運用者の裁定 | 参照の選定は Claude が行う。運用者は従来どおり画像の中から 1 案を選ぶだけ |
| 翻訳での利用 | 分解の対応表に「参照」列を足し、部位ごとに参照ボードの UI 要素を紐づける。DS の既存部品で表現できるかをカタログと見比べ、できなければ ★variant 追加 / ★新部品候補 に分類する。DS 側の Issue には参照リンクを付ける |
| プラットフォームの制約 | 動作環境の制約（アプリ内ブラウザのヘッダー・ログインの位置など）に反する動線は翻訳時に外す |
| 参照が無いとき | 隣の作業で引き直す。それでも無ければ「参照なし」と書いて進む（必須ではない） |
| 件数 | 画面 6〜10 件・フロー 3〜4 件に絞る（結果は画像込みで大きい） |
| 規約表示 | 検索結果に AI 利用の注記（`ai_usage_notice`）が付いたら、そのまま運用者に見せる |
| 接続 | Mobbin のコネクタはセッションの**起動時**に読み込まれる。連携した後に始めたセッションで使う |

参照ボードはフロント Issue に添付して経緯として残す（落選した画像案は破棄）。

## 8. （任意）シェルの決定表

画面の外枠（ヘッダー・ナビ・本文の幅と余白）を「シェル」として固定数用意するなら、
**新しいページは決定表で必ず 1 つのシェルに落ちる**ようにする。「どれにも当てはまらないので自分で組む」を作らない。

| # | 問い（上から順に。最初に「はい」になったものを使う） | シェルの例 |
|---|---|---|
| 1 | 行き止まりの状態表示か（操作は「戻る」「閉じる」程度） | 中央寄せの通知 |
| 2 | 管理者が**特定のテナントの中**で操作する画面か | 管理画面（サイドバー + パンくず） |
| 3 | テナントの文脈が無い状態で、ナビを外して 1 つの作業をさせる画面か | 集中（ナビなし） |
| 4 | 未ログインの訪問者に紹介する・読ませる画面か | マーケティング |
| 5 | 上のどれでもない | 一般アプリ（幅は 作業 / 一覧 / 読み物 で選ぶ） |

- ページは `<main>`・本文の外枠の余白・幅・ヘッダーを自分で書かない（シェルだけが持つ）。lint やテストで機械的に落とす
- **新しいシェルが要りそうなら作らずに運用者に上げる。** 決定表のどの問いで落ちなかったかと、既存シェルの variant で足りない理由を添える
- 発散（§2 の 2）の前にシェルを決め、画像生成のプロンプトに入れる。翻訳（4）はシェルのテンプレートを複製してから組む
