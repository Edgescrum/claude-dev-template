## スタック: ui-figma-ds

フロントの新規画面・レイアウト変更は、**実装前に Figma で確定させる。** 正は **`docs/ui-confirmation-flow.md`**、
発散〜翻訳の実行は `/design-variants` スキル。

プロダクト固有の値（記入）:

| 項目 | 値 |
|---|---|
| 画面モックのファイル（Screen） | `https://www.figma.com/design/{{FIGMA_SCREEN_FILE_KEY}}/` |
| DS ライブラリ | `https://www.figma.com/design/{{FIGMA_LIBRARY_FILE_KEY}}/` |
| DS のカタログ（Storybook 等） | （記入: URL。Evaluator が「DS にその部品があるか」を確かめる場所） |
| DS の正 | （記入: 例「コードが正。トークンは Git 管理の JSON から Figma Variables へ自動同期」） |
| 画像生成の共通コンテキスト | （記入: デバイスと幅 / プロダクトの種類と利用者 / UI の言語 / ブランドの色と雰囲気） |
| 画像生成の API キー | リポジトリ外のローカル env ファイル（リポジトリ・ホスティングに置かない） |
| シェル | 使わない / 使う（決定表は `docs/ui-confirmation-flow.md` §8） |

### 規則

| 規則 | なぜ |
|---|---|
| **どのセッションでも「新しい画面を作って」「レイアウトを変えて」は実装に入らず本フローに回す**（発散 → 運用者の選定 → DS 当てはめで Figma 化 → 乖離裁定 → 確定 → Issue） | 視覚の裁量を実装者に残すと、後から細かな修正が続く |
| フロント系の Issue には `Figma: <ノード URL>` か `Figma 対象外（理由）` の**どちらかを必須**で書く。宣言は起票者、妥当性は Evaluator が検証する | 申告と検算の分離 |
| 文言・既存パターンの踏襲・微調整は対象外 | 小さな変更に重い手順を課さない |
| **運用者の裁定は 3 点だけ**: 画像の選定・乖離の裁定・確定（Mark as ready for dev）。参照の選定や分解は Claude が行う | 運用者の負担を増やさない |
| 画像から持ち込むのはレイアウト構造・情報の優先度・表現の意図だけ。色 / 余白 / 角丸 / 影はトークンにスナップする | トークン外の直書きの発生源を断つ |
| **確定の印は Figma のネイティブ機能「Mark as ready for dev」**。実装がマージされたら Completed | 差分追跡と API（`devStatus`）での機械検証が付いてくる。擬似ステータスは作らない |
| 状態チェックリスト（空 / ローディング / エラー / 最長 / キーボード表示時）を満たしてから確定する。既存パターン名を書けるなら宣言でよい | 状態の未定義が後からの修正を生む |
| **新部品は DS 先行。** DS に無い部品・variant は DS に先に足してから実装する。例外は本番障害級だけで、そのときは `ds-debt` の Issue を同時に起票する（必須） | プロダクト側の先行実装が DS との乖離を固定化する |
| Mobbin の参照は動線と UI 要素だけ。**画像を画像生成に渡さない**・**最低 1 案は参照なし**・引用は `mobbin_url` | 他社アプリの見た目に寄せない / 発散を確保する / 画像 URL は失効する |

### Evaluator の照合（4 点。違反だけが差し戻し理由）

1. 指定された DS 部品が使われているか（カタログで確かめる）
2. レイアウト構造・情報の順序が Figma と一致するか
3. 宣言された状態が全部実装されているか
4. トークン外の直書きの色 / 余白が無いか

美観の微差は「視覚メモ」としてレビューに列挙し、差し戻し理由にしない（運用者が staging で裁定する）。
Issue の「Figma 対象外」宣言が妥当か（実は新しい表現ではないか）も検証する。

### SaaS はネイティブ機能を先に確かめる

Figma・分析・監視・ドキュメント系の SaaS の上に運用ルールや擬似ステータスを**発明する前に**、公式ヘルプとリリースノートで
ネイティブ機能を確かめる。Figma はユーザーレベルのスキル **`figma-docs-first`** を使う。
独自規約を出すときは「ネイティブに無いことを確認済み」と明記する（知識の更新より機能追加のほうが速い）。
