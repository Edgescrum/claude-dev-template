# 運用基盤（エラー監視・行動分析・KPI・通知・死活・問い合わせ）

> **この文書が唯一の置き場所（詳説）。** 規則の要約は CLAUDE.md の「スタック: observability」節。
> 採用しないサービスの節は消してよい。ここに書いたサービス名は「実績のある組み合わせの一例」で、
> 差し替えるときも各節の**規則**（受信側で確かめる・PII を流さない・読者でチャンネルを分ける）は残す。

**大原則: 送信 200 は「どこかに届いた」であって「正しい場所に届いた」ではない。**
鍵・DSN・宛先を取り違えても、送信側はすべて成功を返す。**着地は必ず受信側の件数で確かめる。**

---

## 1. エラー監視（Sentry）

| 規則 | なぜ |
|---|---|
| **DSN が正しいプロジェクトを指しているかを、受信側（Sentry のプロジェクトのイベント数）で確かめる** | 削除済み・別のプロジェクトの DSN でも送信側は気づかない。ブラウザのコンソールに 403 が出るだけで、エラーが長期間全損しうる |
| **DSN と auth token は別物として扱う。** DSN = イベント送信用（公開してよい・`NEXT_PUBLIC_` 可）、auth token = リリース・ソースマップのアップロード用（秘匿・CI だけ） | リリースは auth token + プロジェクトのスラッグ経由で届くので、**DSN が壊れていてもリリースだけは届き、「動いている」ように見える** |
| 環境（production / staging / preview）をタグで分け、アラートは production だけにする | 開発のノイズで本番の初報が埋もれる |
| 送信前に PII（氏名・電話・メール・トークン）を落とす。例外メッセージに個人情報を入れない | エラー監視は個人情報の保管庫ではない |
| **cron の不実行は Cron Monitor（チェックイン）で検出する**（エラー監視とは別の仕組み） | 「走らなかった」はエラーを出さない |

### 開発チャンネルへの中継

- アラートの通知先として webhook を使うなら、**現行のネイティブな経路**（Internal Integration のアラートアクション等）を
  公式ドキュメントで確かめてから使う。古い webhook 連携は廃止されていることがある
- 中継エンドポイントを自前で置くなら:
  - 認証は推測不能なトークン（定数時間比較・設定が無ければ拒否する fail-closed）。署名検証が提供されていればそれを使う
  - **転送する項目を allowlist で決める**（タイトル・発生箇所・レベル・環境・URL・ルール名）。リクエスト本文・ユーザー・パンくず・例外の中身は読まない
  - 認証失敗以外は常に 200 を返す（送信側の再送連打を避ける）。失敗はログに残す
  - エラー系の通知は**この 1 本道だけ**にする（アプリから直接チャンネルに投げる経路を並べない。重複は読まれなくなる）

## 2. 行動分析（PostHog）

| 規則 | なぜ |
|---|---|
| **staging と本番でプロジェクト（＝キー）を分ける** | 混ざると本番の数字が汚れ、stg の緩い設定が本番で動く |
| どちらのプロジェクトに送るかは 1 つの環境変数（プロファイル）で切り替え、**未設定なら本番側（厳しいマスキング）に倒す** | 設定漏れが「緩い設定で本番」にならないように |
| **本番はセッションリプレイを無効、全テキストと要素属性をマスク**する。staging は緩めてよい | 画面の録画・テキストは個人情報を含む |
| **匿名の利用者を person として作らない**（`person_profiles: 'never'`、識別する設計なら識別後だけ） | 匿名の person は無料枠を食い、識別子が個人情報に寄る |
| **自動収集（autocapture）に頼らず、計測は opt-in にする。** クリックの意味は `data-ph-capture-attribute-action="<固定の英字リテラル>"` で付け、ファネルのイベントは allowlist で管理する | 自動収集の要素チェーン（属性・テキスト）から氏名や `tel:` が漏れうる。値に変数を入れると同じ経路で漏れる |
| **着地は Query API（件数）で確かめる。送信の HTTP 200 では確かめない** | キーを取り違えると、別プロジェクトに 200 で届く |
| 請求の上限（billing limit）を低額に設定して実質のハードキャップにする | 想定外の流量で課金が膨らまない |
| クライアント IP を保存しない設定にする | 不要な個人データを持たない |
| ログイン後は事業者 ID 等の**非個人の**グループ属性を付ける。匿名性は保つ | テナント単位の分析ができる |

- 分析 SDK は**自動操作のブラウザをボットと判定してイベントを黙って捨てる**ことがある。Playwright 等で着地を確かめられないので、
  実トラフィックで Query API の件数を見る
- 診断・ダイジェスト用の **read-only の個人 API キー**（クエリ読み取りだけ・対象プロジェクトだけ）を作り、
  ローカルではリポジトリ外の env ファイル（例: `~/.config/<project>/posthog.env`）に、ホスティングでは秘匿の環境変数に置く

## 3. KPI の時系列（DB 内の日次テーブル）

- **1 日 1 行の KPI テーブルを DB に置き、削除しない（永久保存）。** 行動分析のサービスの保持期間・料金・乗り換えに左右されない
- 日次 cron で集計する。**集計窓は業務のタイムゾーンで切る**（UTC で切ると日付がずれる）。**冪等**（同じ日を再実行しても 1 行）
- 列の例: 事業者数（プラン別）・利用者数・取引数・売上・外部サービスの消費量（送信枠など）・**DB の容量**（膨張の監視）
- 容量は 1 行数百バイト程度なので、年単位でも問題にならない

## 4. 運用通知（Discord の 3 チャンネル）

**読者でチャンネルを分ける。** 読者が違う通知を混ぜると、どちらも読まれなくなる。

| チャンネル | 読者 | 流すもの | 環境変数（例） |
|---|---|---|---|
| `#dev-errors` | 技術者 + Claude | エラーの初報（§1 の中継）・死活監視の通知 | `DISCORD_WEBHOOK_URL` |
| `#ops-alerts` | 事業側（即応） | 問い合わせの新着・課金イベント（契約・解約・支払い失敗）・外部サービスの上限警告 | `DISCORD_WEBHOOK_URL_ALERTS` |
| `#ops-digest` | 事業側（定期） | **週次の戦略ダイジェスト**・新規登録・半年ごとの期限棚卸し | `DISCORD_WEBHOOK_URL_DIGEST` |

**流さないもの:** cron の成功ログ・取引 1 件ごとの通知・デプロイ通知（読まれなくなり、本当の警告が埋もれる）。

### 週次の戦略ダイジェスト（月曜の朝）

ユニットエコノミクスの体系で並べる。**数字の出どころ**（決済サービスの API / 分析 / KPI テーブル）を各行に決めておく。

| 区分 | 指標 |
|---|---|
| A 収益 | **MRR の分解**（New / Expansion / Contraction / Churned → Net。決済サービスの API から直接）・ARPA・Quick Ratio |
| B 獲得 | 新規登録・トライアルの転換と期限接近・**アクティベーションの完走**（登録 → 初期設定 → 最初の価値） |
| C 定着 | WAU・**一定期間アクセスの無い事業者の名指し**・顧客のリピート率（事業者別のワースト）・機能別の連続ゼロ週 |
| 月初のみ | **チャーン率（3 ヶ月移動平均のみ。単週の % は出さない）**・NRR・LTV の推定・決済の取扱高 |

- 件数が少ないうちの比率はぶれる。**母数が小さい（例 n < 50）指標は「参考値」と明示する**
- 日次の集計（KPI テーブル・上限警告）は日次のまま回し、**投稿だけ週次**にする

## 5. 死活監視

| 監視 | 何を見るか | 通知先 |
|---|---|---|
| 外形監視（UptimeRobot 等・5 分間隔） | サイトのトップと **health エンドポイント（DB への疎通を含む）** | `#dev-errors` |
| cron の実行監視（Cron Monitor） | 予定した cron が**走ったか** | `#dev-errors` |

外形監視は「応答するか」、cron 監視は「走ったか」を見る。片方で両方は見られない。

## 6. 期限の棚卸し（半年ごと）

ドメイン・証明書・API キー・アクセストークン・支払いカード・無料枠の条件は、**期限切れでも事前にエラーを出さない**。
4/1 と 10/1 に cron で `#ops-digest` へ棚卸しのリマインダーを投稿し、`docs/runbooks/periodic-ops-checklist.md` を順に確かめる。

## 7. 問い合わせ（Notion を正にする）

| 規則 | なぜ |
|---|---|
| **問い合わせの正（SSoT）は製品 DB とは別の Notion データベース**に置く | 問い合わせの個人情報を製品 DB から分離する（サポート都合のスキーマ変更を製品の経路に通さない）・ボード UI が無料・**非技術者にも共有できる**・Claude が API で読み書きできる |
| 入口は公開フォームで、**入口で構造化する**（種別・本文・返信先・関係する事業者） | 後から分類する手間を減らす |
| 新着は `#ops-alerts` に通知する。**Notion への書き込みが失敗したら、Discord に全文を載せる** | 消失ゼロ |
| **返信は自動送信しない。** 下書きまで作り、送信は運用者がメールから行う | 誤送信を防ぐ |
| プライバシーポリシーの委託先に Notion を追記する | 個人情報の第三者提供 |
| Notion のプロパティ名・型はコードの定数と一致させ、API で照会して確かめる | 名前のずれは書き込みエラーにならず欠落する |

月数件の規模なら製品 DB との JOIN は不要（仕分け時にメールで照会する）。

## 8. 鍵の扱い（共通）

- ホスティングの Sensitive 型の変数は**読み返せない。** webhook URL・トークン・API キーの控えは運用者がパスワード管理ツールに保管する
- 紛失したら再生成し、**送信側と受信側の両方**を差し替える
- 運用設計（ステータス管理・通知の形）を発明する前に、各サービスの**ネイティブ機能**を公式ドキュメントで確かめる
