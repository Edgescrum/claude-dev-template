# スタック部品: observability（PeCo 由来）

運用開始後に要る基盤（エラー監視・行動分析・KPI の時系列・運用通知・死活監視・期限の棚卸し・問い合わせ）の規則。

## 何を扱うか

- 「送信 200 は『どこかに届いた』であって『正しい場所に届いた』ではない」— 着地を受信側で確かめる規則
- Sentry: DSN と auth token の違い・受信側での確認・中継の作り方・Cron Monitor
- PostHog: staging / 本番のプロジェクト分離・本番のマスキング・匿名 person を作らない・opt-in 計測・Query API での着地確認
- DB 内の日次 KPI テーブル（永久保存）
- Discord の 3 チャンネル（読者で分ける）と週次の戦略ダイジェスト（ユニットエコノミクス）
- 外形監視と cron 監視
- 半年ごとの期限棚卸し
- 問い合わせの正を製品 DB と分けて Notion に置く

## いつ選ぶか

- 本番運用を始めるプロジェクト全般（初期化の 0-9「運用基盤」で採用するものを選ぶ）
- 個々のサービスは差し替えてよい。差し替えても各節の**規則**は残す

## CI に足すもの

拡張点 `scripts/gate-extra.d/*.sh` には何も足さない。分析の opt-in（`data-ph-capture-attribute-action` の値が固定リテラルであること・
ファネルイベントが allowlist にあること）を機械で守るなら、プロジェクトの lint / 単体テストとして置き、標本を添える。

## 初期化でやること（運用者の作業を含む）

- 各サービスのアカウント・プロジェクト（行動分析は staging / 本番の 2 つ）・鍵の発行
- Discord の 3 チャンネルと webhook、外形監視の登録
- 各サービスの無料枠・上限・**超えたら何が起きるか**を `docs/bootstrap.md` の上限表に記録
- 鍵の控えの保管場所を決める（Sensitive 型は読み返せない）
