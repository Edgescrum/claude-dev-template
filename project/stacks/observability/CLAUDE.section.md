## スタック: observability

エラー監視・行動分析・KPI の時系列・運用通知・死活監視・問い合わせの基盤。詳説は **`docs/observability.md`（唯一の置き場所）**。
採用しているサービス（記入）:

| 役割 | サービス | 環境ごとの分け方 |
|---|---|---|
| エラー監視 | （例: Sentry） | 1 プロジェクト + environment タグ |
| 行動分析 | （例: PostHog） | **staging / 本番で別プロジェクト** |
| KPI の時系列 | DB 内の日次テーブル（例: `metrics_daily`） | 本番のみ |
| 運用通知 | （例: Discord の 3 チャンネル） | — |
| 死活 | （例: UptimeRobot + Cron Monitor） | 本番のみ |
| 問い合わせの正 | （例: Notion データベース） | — |

### 大原則

- **送信 200 は「どこかに届いた」であって「正しい場所に届いた」ではない。** 鍵・DSN・宛先を取り違えても送信側は成功を返す。
  **着地は受信側の件数で確かめる**（エラー監視ならプロジェクトのイベント数、分析なら Query API の件数）
- 運用の仕組み（ステータス・通知の形・ハンドオフ）を発明する前に、**各サービスのネイティブ機能を公式ドキュメントで確かめる**
- 個人情報を監視・分析・通知に流さない。流す項目は allowlist で決める

### エラー監視

| 規則 | なぜ |
|---|---|
| DSN が正しいプロジェクトを指しているかを受信側で確かめる | 削除済みプロジェクトの DSN でもアプリは気づかず、エラーが全損する |
| DSN（送信用・公開可）と auth token（リリース・ソースマップ用・秘匿）を混同しない | DSN が壊れていてもリリースだけは届き、動いているように見える |
| アラートは production だけ。通知は `#dev-errors` への 1 本道（重複経路を作らない） | ノイズと重複は読まれなくなる |
| 中継を置くなら、トークン認証（定数時間比較・fail-closed）・転送項目の allowlist・認証失敗以外は 200 | PII を流さず、再送連打を避ける |
| cron の不実行は Cron Monitor で見る | 走らなかったことはエラーを出さない |

### 行動分析

| 規則 | なぜ |
|---|---|
| staging / 本番でプロジェクトを分け、1 つのプロファイル変数で切り替える。**未設定なら本番側（厳しい設定）に倒す** | 設定漏れで緩い設定が本番で動かないように |
| 本番はセッションリプレイ無効・全テキストと要素属性をマスク | 録画とテキストは個人情報を含む |
| 匿名の利用者を person にしない（`person_profiles: 'never'`） | 無料枠と個人情報 |
| **計測は opt-in。** `data-ph-capture-attribute-action="<固定の英字リテラル>"` と、ファネルイベントの allowlist で行う。値に変数を入れない | 自動収集の要素チェーンから氏名・電話が漏れうる |
| 着地は Query API の件数で確かめる。自動操作のブラウザはボット判定で捨てられるので、実トラフィックで見る | 200 は着地の証明にならない |
| read-only の個人 API キー（クエリ読み取り・対象プロジェクトだけ）は、リポジトリ外の env ファイルに置く | 診断・ダイジェストで使う |
| billing limit を低額に設定する | 想定外の流量でも課金が膨らまない |

### KPI と通知

- **KPI は DB の日次テーブルに 1 日 1 行で永久保存する**（業務のタイムゾーンで集計・冪等・DB 容量の列を含める）
- 通知は**読者で 3 チャンネルに分ける**: `#dev-errors`（技術者: エラー初報・死活）/ `#ops-alerts`（事業側・即応: 問い合わせ・課金イベント・上限警告）/
  `#ops-digest`（事業側・定期: 週次の戦略ダイジェスト・新規登録・期限棚卸し）
- **流さない**: cron の成功ログ・取引 1 件ごと・デプロイ通知
- 週次ダイジェストはユニットエコノミクスで並べる（MRR の分解・獲得とアクティベーション・定着）。
  **チャーン率は 3 ヶ月移動平均のみ（単週の % は出さない）**。母数の小さい指標は参考値と明示する
- 死活は外形監視（サイト + DB 疎通を含む health・5 分間隔）と cron 監視の 2 本立て
- 4/1・10/1 に期限棚卸しのリマインダーを投稿し、`docs/runbooks/periodic-ops-checklist.md` を通す

### 問い合わせ

- **正は製品 DB とは別の Notion データベース**（個人情報の分離・非技術者と共有・ボード UI）。入口のフォームで構造化する
- 新着は `#ops-alerts`。**Notion への書き込みが失敗したら Discord に全文を載せる**（消失ゼロ）
- 返信は自動送信しない（下書きまで。送信は運用者）
- プライバシーポリシーの委託先に追記する

### 鍵

ホスティングの Sensitive 型の変数は読み返せない。webhook URL・トークン・API キーの控えは運用者が保管し、
紛失したら再生成して**送信側と受信側の両方**を差し替える。
